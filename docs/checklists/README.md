# 구현 체크리스트 안내

기반 문서: [`docs/specs/annswieteom_detailed_spec.md`](../specs/annswieteom_detailed_spec.md)
마감: 2026-09-20

이 디렉터리는 명세서를 실제 구현 작업 단위로 쪼갠 체크리스트 모음이다. **담당자 기준으로 폴더를 나눴다**:

| 폴더 | 담당 | 역할 |
|---|---|---|
| [`00_shared/`](00_shared/) | 공용(둘 중 아무나 / 함께) | 리포지토리 스캐폴딩, DB 스키마, 배포 설정 |
| [`person_A_infra_ai/`](person_A_infra_ai/) | **A** (로컬 추론 서버(DGX Spark) 운영 담당, 서버 운영 경험 없음) | 로컬 LLM·임베딩 서빙, AI 어댑터, 기록물 파이프라인, Cloudflare Tunnel, 일관성 검증, 서버 운영 |
| [`person_B_frontend_backend/`](person_B_frontend_backend/) | **B** | 인증 API, 인터뷰 상태머신 API, 기록물/문서 생성 API, 프론트엔드 전체 |
| [`milestones_overview.md`](milestones_overview.md) | 둘 다 | 주차별 마일스톤과 위 체크리스트 항목들의 매핑, 검증 기준 |

## 사용 방법

1. 아직 서버 운영 경험이 없는 사람이 A라면, `person_A_infra_ai/README.md`부터 읽는다.
2. 각 체크리스트 파일은 위에서 아래로 순서대로 처리하면 되도록 정렬했다. 항목 옆 괄호는 근거가 되는 명세서 절 번호다.
3. 체크리스트를 실제로 완료할 때마다 `- [ ]`를 `- [x]`로 바꿔 진행 상황을 기록한다.
4. `00_shared/`의 작업(특히 DB 스키마)이 끝나야 A/B 폴더의 후속 작업을 시작할 수 있는 경우가 많으니, 폴더 번호(00 → person_A/person_B) 순서를 크게 벗어나지 않는 게 좋다.
5. 각 체크리스트 파일 상단의 "브랜치:" 항목을 보고 어떤 Git 브랜치에서 작업할지 확인한다. 전체 브랜치 전략(`main`/`dev`/`feature/*` 구조와 승격 시점)은 [00_shared/01_repo_and_env_setup.md](00_shared/01_repo_and_env_setup.md) 4절에 정리돼 있다.

## 절대 원칙 — 모든 폴더 공통 (명세서 1-2절)

> **정직성 가드레일**: 사용자가 명시적으로 확인/작성하지 않은 내용, 또는 사용자의 개인 기록물에 실제로 존재하지 않는 내용은 최종 생성물에 절대 포함되면 안 된다. 최종 문서 생성 함수는 오직 `confirmed_facts` 테이블에 저장된 사실만 입력으로 받을 수 있어야 한다.

이 원칙은 A(프롬프트·일관성 검증)와 B(문서 생성 API·상태머신) 양쪽 작업 모두에 걸쳐 있다. 어느 체크리스트를 진행하든 이 원칙을 깨는 코드 경로(예: `confirmed_facts`를 거치지 않고 AI 초안이 바로 최종 문서에 들어가는 경로)를 만들지 않았는지 항상 확인한다.
