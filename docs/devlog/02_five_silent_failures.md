# 다섯 겹의 침묵

[01_from_engine_to_the_real_world.md](01_from_engine_to_the_real_world.md)에서 우리는 13단계까지 왔다 — 서비스를 실제로 인터넷에 띄우고, 처음 만난 진짜 버그(AI가 형식을 안 지켰을 때 서버가 죽던 문제)까지 고쳤다. 그런데 배포가 끝났다고 일이 끝난 게 아니었다. 오히려 그때부터가 진짜 시작이었다 — 개발 중에는 안 보이던 문제들이, 실제 사용자가 쓰는 상황에서만 모습을 드러냈기 때문이다.

이 글은 두 부분으로 나뉜다. 앞부분(14~17단계)은 화면을 더 쓰기 편하게 다듬은 기록이고, 뒷부분(18단계)은 "날짜를 입력하면 에러가 난다"는 사용자 신고 하나를 파고들었더니 **서로 다른 다섯 개의 원인이 겹겹이 숨어 있었던** 하루짜리 탐정 이야기다. 특히 뒷부분은, 겉으로 보이는 증상(에러 메시지) 하나만 보고 "고쳤다"고 믿으면 왜 위험한지를 아주 잘 보여준다.

## 14단계 — 세션에 이름을 붙이고 지울 수 있게, 그리고 집 안 정리를 하다

사용자가 세션(공백기 인터뷰 하나의 진행 단위)을 여러 개 만들 수 있게 되면서, 사이드바에 세션이 여러 개 쌓이기 시작했다. 그런데 각 세션은 그냥 생성된 날짜(`2026. 9. 4.`)로만 구분됐다 — "육아 공백기"인지 "이직 준비 공백기"인지 열어보기 전엔 알 수 없었다. 그래서 이름을 직접 붙이고(rename), 필요 없어지면 지울 수 있게(delete) 만들었다.

재미있게도 삭제 기능은 뒷단(백엔드) API가 이미 만들어져 있었는데 화면에 버튼만 없던 상태였다. 반면 이름 변경은 데이터베이스에 이름을 담을 칸(`title` 컬럼)조차 없어서 처음부터 만들어야 했다. 이렇게 데이터베이스의 구조를 바꾸는 작업을 **마이그레이션**이라고 부르는데, 이건 되돌리기 까다로울 수 있는 작업이라 실제 운영 중인 데이터베이스에 적용하기 전에는 항상 한 번 더 확인하고 진행했다.

### 왜 갑자기 "구조 정리"를 했나

기능 하나를 추가하는 김에, "앞으로 기능이 더 많이 늘어나도 이 구조가 버틸 수 있을까?"를 점검했다. 두 가지를 특히 손봤다.

첫째, **의존성 주입(DI, Dependency Injection)** 훅의 위치. 이 프로젝트는 "AI에게 물어보기", "이미지 저장소에 접근하기" 같은 기능을 실제로 사용하는 코드가 직접 그 기능을 만들지 않고, "이걸 준비해줘"라고 요청하면 FastAPI가 대신 준비해서 건네주는 방식을 쓴다. 이렇게 하면 테스트할 때 진짜 AI 대신 가짜 AI로 슬쩍 바꿔치기하기 쉽다. 그런데 "AI를 준비해주는 함수"가 원래 있어야 할 자리(AI 관련 코드 폴더)가 아니라 엉뚱하게 다른 기능(인터뷰 화면)의 코드 안에 끼어 들어가 있었다. 그러다 보니 문서 생성 기능이 AI를 쓰려면 인터뷰 화면의 코드를 몰래 가져다 써야 하는, 서로 얽히면 안 될 두 기능이 얽히는 모양이 됐다. 제자리로 옮겼다.

둘째, 파일 하나에 너무 많은 게 뒤섞여 있던 것들을 나눴다. 백엔드는 "이 기능(예: 기록물 업로드)을 다루는 API 코드"와 "그 API가 주고받는 데이터 형식을 정의한 코드"가 항상 1:1로 짝지어 있어야 나중에 찾기 쉬운데, 딱 한 군데만 이 규칙이 깨져 있었다. 프론트엔드도 "백엔드와 통신하는 코드" 전부가 481줄짜리 파일 하나에 뭉쳐 있었는데, 기능별로 5개 파일로 나눴다(기존 파일은 그대로 두고 안에서 새 파일들을 다시 내보내주는 방식을 써서, 이 파일을 갖다 쓰던 다른 코드는 한 줄도 안 고쳐도 되게 했다).

이렇게 정리한 구조를 그림과 표로 남긴 문서가 [docs/architecture.md](../architecture.md)다. 다음에 이 프로젝트에 뭔가를 추가하려는 사람이 "이건 어디에 둬야 하지?"라고 헷갈릴 때 참고할 수 있게 만들었다.

## 15단계 — 화면에 눈에 안 보이는 글자가 있었다 (다크 모드)

사용자가 어두운 배경 테마(다크 모드)로 화면을 보면, 채팅 말풍선 안의 글자가 안 보인다는 문제가 있었다. 원인은 이렇다: 화면 전체의 배경/글자색은 "지금 밝은 테마인지 어두운 테마인지"에 따라 자동으로 바뀌게 만들어뒀는데, 말풍선 하나하나의 배경색은 그 규칙과 상관없이 그냥 "흰색", "연한 회색"처럼 못박아 놓았다. 그러다 보니 어두운 테마에서는 "말풍선 배경은 그대로 밝은 회색인데, 그 안의 글자색만 어두운 테마용 밝은 색으로 바뀌어서 밝은 배경 위에 밝은 글자"가 겹쳐 안 보이게 된 것이다.

고친 방법은, 배경색과 글자색을 항상 짝으로 묶어서 테마에 따라 같이 바뀌게 만든 것이다. "이 말풍선은 밝은 테마에서는 회색 배경+검은 글자, 어두운 테마에서는 진회색 배경+흰 글자"처럼 짝 전체를 하나의 이름으로 저장해두고, 코드에서는 그 이름만 갖다 쓰게 했다. 이러면 배경만 바뀌고 글자색이 안 따라오는 실수 자체가 구조적으로 안 생긴다.

## 16단계 — 서버가 낮잠 잘 때 사용자에게 뭐라고 말해줄까

뒷단 서버를 무료로 올려둔 곳(Render)은, 15분 동안 아무 요청도 없으면 서버를 잠재워버린다. 서버 비용을 아끼려는 정책인데, 문제는 사용자가 오랜만에 다시 접속했을 때 이 잠든 서버를 깨우는 데 최대 1분 가까이 걸릴 수 있다는 점이다. 그동안 화면에는 그냥 "불러오는 중..."이라는 글자만 떠 있어서, 사용자 입장에서는 "이거 멈춘 거 아닌가?"라고 오해하기 딱 좋았다.

그래서 로딩이 4초 넘게 계속되면, "서버가 잠시 쉬고 있다가 깨어나는 중일 수 있어요. 최대 1분 정도 걸릴 수 있으니 조금만 기다려주세요"라는 안내 문구를 추가로 보여주게 했다. 평소처럼 서버가 이미 깨어 있어서 빠르게 응답할 때는 이 문구가 아예 뜨지 않는다 — 4초라는 문턱값을 넘을 때만 나타난다.

## 17단계 — 로그인하면 바로 들어가지도록

원래는 로그인에 성공하면 "새로 시작하기"라는 버튼 하나만 있는 화면으로 이동했다. 그런데 이미 진행 중인 세션이 있는 사용자 입장에서는, 버튼을 한 번 더 눌러야 세션 목록이 있는 화면으로 들어갈 수 있는 게 불필요한 한 단계였다. 그래서 로그인하면(또는 로그인된 상태로 이 화면을 다시 방문하면) 자동으로 가장 최근 세션으로 바로 들어가게 바꿨다 — 세션이 하나도 없는 신규 사용자라면 그 자리에서 새 세션을 하나 만들어서 들여보낸다.

이렇게 바꾸면 기존 버튼이 있던 화면 자체를 더 이상 보여주지 않게 되는데, 그러면 "세션이 이미 여러 개 있는 상태에서 새 세션을 하나 더 만들고 싶을 때" 누를 버튼이 없어져 버린다. 그래서 그 버튼을 세션 목록이 있는 사이드바 쪽으로 옮겨서("+ 새 세션"), 기능 자체는 그대로 남겨뒀다.

## 18단계 — "날짜를 입력하면 에러가 나요": 다섯 겹의 침묵을 벗겨낸 하루

여기서부터가 이 글의 핵심이다. 사용자로부터 "실제 사이트에서 인터뷰 첫 단계(공백기 날짜 입력)를 하면 에러가 난다"는 신고가 들어왔다. 처음엔 간단한 버그 하나겠거니 했는데, 실제로는 서로 다른 층위에 있는 다섯 개의 문제가 순서대로 겹쳐 있었다. 하나를 고치면 증상이 살짝 바뀌면서 다음 문제가 드러나는 식이었다. 이 과정을 그대로 남기는 이유는, **"에러 메시지 하나만 보고 원인을 하나로 단정하면 안 된다"**는 걸 이보다 잘 보여주는 사례가 없기 때문이다.

### 18-1. 첫 번째 겹 — CORS 에러처럼 보였지만, 사실은 서버가 넘어진 것이었다

배포된 사이트에서 날짜를 입력하면 브라우저 개발자 도구에 이렇게 떴다: `CORS policy에 의해 차단됨`. **CORS**란 "지금 보고 있는 웹사이트와 다른 주소로 요청을 보낼 때, 그 다른 주소 쪽 서버가 미리 허락해뒀는지"를 브라우저가 검사하는 보안 규칙이다. 그래서 처음엔 서버의 허용 목록 설정이 잘못됐나 싶었다.

그런데 이상한 점이 있었다. 같은 서버로 보내는 다른 요청들(로그인, 세션 목록 조회 등)은 전부 멀쩡했고, 딱 "날짜 추출" 요청 하나만 이 에러가 났다. CORS 설정이 통째로 잘못됐다면 모든 요청이 다 막혔어야 한다. 직접 서버 코드를 다시 훑어보니 진짜 원인이 드러났다: 서버가 AI(Gemini)에게 물어볼 준비를 하는 과정에서, **API 키가 비어있으면 그 순간 프로그램이 그대로 멈춰버리는(예외가 처리되지 않고 튀어나오는)** 코드가 있었다. 문제는 이 멈춤이 일어나는 시점이 너무 일러서, "이 요청은 어디서 왔으니 허락한다"는 CORS 허용 표시를 아직 붙이기도 전에 서버가 죽어버린 것이었다. 그러니 브라우저 입장에서는 "허락 표시가 아예 없는 응답"을 받은 셈이 되고, 이걸 CORS 위반으로 오해해서 표시한 것이다. **진짜 원인은 CORS가 아니라, 서버가 미처 정리도 못 하고 넘어진 것**이었다.

고친 방법: API 키가 실제로 필요한 순간까지 AI 연결 준비를 미루도록(**즉시 준비 대신 필요할 때 준비하기**, lazy initialization이라고 부른다) 바꿨다. 이러면 준비 과정에서 실패해도, 이미 만들어져 있던 "이 AI가 실패하면 다음 AI로 넘어가라"는 정상적인 처리 경로를 그대로 탈 수 있다.

### 18-2. 두 번째 겹 — 존재하지 않는 모델의 이름을 부르고 있었다

첫 번째 문제를 고치고 나니 에러가 좀 더 솔직해졌다: 이제는 CORS 대신 "AI 서버에 연결할 수 없습니다"라는, 원래 의도했던 정상적인 에러 메시지가 떴다. 그런데 여전히 실패였다. 로그를 남기게 코드를 고쳐서 다시 보니, 코드 안에 기본값으로 박혀 있던 로컬 AI 모델 이름(`exaone3.5:7.8b`)이 실제 서버에 설치된 모델 이름(`exaone3.5:latest`)과 미묘하게 달랐다. 사람이 보기엔 "그게 그거 아닌가" 싶지만, 컴퓨터는 정확히 똑같은 이름이 아니면 "그런 모델 없음"이라고 답한다. 게다가 이 기본값은 프로젝트 설정 안내서(`.env.example`)에 적힌 값과도 서로 달랐다 — 애초에 둘이 안 맞았던 것이다. 실제로 서버에 설치된 모델 이름으로 정확히 맞춰서 고쳤다.

### 18-3. 세 번째 겹 — 텅 빈 설정값 하나가 "다음 AI로 넘어가기" 기능 자체를 꺼버렸다

또 고쳤는데 또 실패였다. 이번엔 로그에 아무 단서도 안 남았다 — "이 AI가 실패했다"는 흔적조차 없이 바로 "전부 실패"로 끝나 있었다. 원인을 추적해보니: 이 서비스는 "로컬 AI, 그다음 Gemini" 순서로 시도하라는 설정값(`LLM_PROVIDER_ORDER=local,gemini`)을 갖고 있는데, 실제 서버에 이 값이 **완전히 빈 문자열**로 들어가 있었다. 빈 문자열을 순서 목록으로 해석하려니 아무것도 안 남았고, 그러면 "시도해볼 AI가 하나도 없다"는 뜻이 되어, 뭘 시도해보지도 않고 곧바로 실패 처리가 된 것이다. 시도한 흔적이 없으니 로그도 안 남았던 것이다.

이 참에 설정값에 대소문자가 섞이거나(`Local,Gemini`) 빈칸이 섞여도 문제없이 인식하도록 코드를 더 튼튼하게 고치고, 혹시라도 "시도해볼 AI가 하나도 없는" 상황이 되면 그 자체를 눈에 띄는 로그로 남기게 만들었다. 같은 방식의 실수가 다음에 또 나도 이번처럼 한참 헤매지 않도록 하기 위해서다.

### 18-4. 네 번째 겹 — 서버는 멀쩡한데, 아무도 문을 열어주지 않았다

여기까지 고치고 나니 마침내 진짜 원인이 로그에 찍혔다: `403 Forbidden`. 그런데 같은 주소로 다른 곳(개발자 컴퓨터)에서 직접 불러보면 멀쩡히 잘 됐다. **딱 배포된 서버가 부를 때만** 거부당했다.

이 대목에서 진짜 서버용 컴퓨터(RTX 4090이 달린 그 컴퓨터)의 상태도 같이 점검했는데, 뜻밖의 사실을 하나 더 발견했다. 컴퓨터를 껐다 켜도 터널이 자동으로 살아나게 등록해둔 "서비스"가, 겉보기엔 "실행 중"이라고 표시돼 있었지만 실제로는 아무 연결도 붙잡고 있지 않았다 — 그날그날 사람이 손으로 띄워둔 임시 프로그램이 대신 연결을 붙잡고 있었을 뿐이었다. [01_from_engine_to_the_real_world.md 9단계](01_from_engine_to_the_real_world.md)에서 겪었던 것과 같은 종류의 문제였다. 이건 서비스를 다시 등록해서 고쳤다.

하지만 그렇게 고치고 나서도 403은 그대로였다. 진짜 원인은 다른 곳에 있었다: 이 프로젝트가 쓰는 도메인 관리 서비스(Cloudflare)가, 배포 서버(Render)처럼 "일반 개인 인터넷 회선이 아닌 곳"에서 오는 요청을 자동으로 "혹시 이거 사람이 아니라 봇 아닐까?"라고 의심해서, 사람만 풀 수 있는 확인 절차(자바스크립트를 실행해야 통과되는 "Just a moment..." 페이지)를 끼워 넣고 있었다. 우리 백엔드는 사람이 아니라 프로그램이니 이 확인 절차를 절대 통과할 수 없다 — 서버 몇 대가 서로 대화하는 API 호출인데 "당신이 사람인지 증명하라"는 페이지를 만난 셈이다.

이건 코드로 고칠 수 있는 문제가 아니라, Cloudflare의 보안 설정을 직접 조정해야 하는 문제였다. 처음엔 "이 주소로 오는 요청은 봇 검사를 건너뛰어라"는 규칙을 하나 추가했는데도 여전히 막혔다 — 알고 보니 그 봇 검사 기능 자체가 "규칙으로 건너뛸 수 있는 종류"가 아니라, 계정 전체에 걸린 더 기본적인 스위치(Bot Fight Mode)였다. 그 스위치를 직접 끄고 나서야 마침내 통과됐다.

### 18-5. 다섯 번째 겹 — 문서를 생성하는 버튼을 눌렀더니, 똑같은 유령이 또 나왔다

날짜 입력은 완전히 고쳐졌다. 그런데 뒤이어 "인터뷰 질문에 전부 답했는데, 최종 문서가 생성이 안 된다"는 사용자 신고가 또 들어왔다. 실제로 처음부터 끝까지 인터뷰를 다시 진행해보니, 정말로 마지막 "문서 생성" 버튼에서만 0.6초 만에 실패했다 — AI에게 뭔가를 물어보고 답을 기다리기엔 너무 짧은 시간이었다.

같은 조건으로 우리 컴퓨터에서 직접 재현해보니 오히려 멀쩡하게 성공했다. 이게 결정적인 단서였다: **똑같은 코드가 한쪽(우리 컴퓨터)에서는 되고, 다른 쪽(배포 서버)에서는 안 된다면, 코드가 아니라 두 환경의 설정 차이를 의심해야 한다.** 실제로 확인해보니, 18-1에서 고쳤던 바로 그 버그가 **다른 파일에 판박이로 하나 더 남아있었다.** 문서를 만들 때 AI가 지어낸 이야기를 안 하는지 마지막으로 검사하는 기능("정직성 검증", [00_project_kickoff.md 6단계](00_project_kickoff.md) 참고)도 AI를 쓰는데, 이 기능을 준비하는 코드에 똑같이 "API 키가 비어있으면 그 자리에서 바로 멈춰버리는" 실수가 그대로 복사돼 있었던 것이다. 다만 인터뷰 화면 쪽 코드는 이 실패를 감싸서 무시하는 안전장치가 있었던 반면, 문서 생성 쪽에는 그 안전장치가 없어서 이번에만 겉으로 드러난 것이었다. 18-1과 완전히 같은 방식으로 고쳤다.

### 왜 이렇게 오래 걸렸나 — 로깅이라는 손전등

다섯 겹을 다 벗기고 나니 하나 확실해진 게 있다. 이 문제들이 오래 걸린 진짜 이유는 버그 하나하나가 어려워서가 아니라, **실패했을 때 "왜 실패했는지"가 어디에도 안 남아 있었기 때문**이었다. 서버는 "실패했다"까지만 사용자에게 알려주고, "누가, 왜 실패했는지"는 자기만 알고 아무 데도 적어두지 않는 코드가 많았다. 그래서 이번 하루 동안 고친 것 중 절반은 사실 버그 수정이 아니라, **다음에 비슷한 일이 생기면 훨씬 빨리 원인을 찾을 수 있도록 실패 이유를 기록(로그)으로 남기는 작업**이었다. 어두운 방에서 물건을 찾을 때, 불을 한 번 켜두면 다음부터는 더듬거릴 필요가 없어지는 것과 같다.
