# 22~25단계 — 로컬 개발 환경 분리, velog 목록 가져오기, 그리고 인터뷰가 멈추던 진짜 이유들

[04_new_face_and_the_trapped_loading_screen.md](04_new_face_and_the_trapped_loading_screen.md) 이후, 로컬 노트북에서 실제로 인터뷰를 돌려보기 시작하면서 코드로만 보일 땐 안 보이던 문제들이 하나씩 튀어나왔다. 이 글은 로컬/프로덕션 환경을 분리한 것부터, velog 목록 페이지 가져오기, 인터뷰가 같은 질문을 반복하던 버그, 그리고 프로덕션에서 실제로 신고받은 "게스트 세션이 두 개가 되는" 문제까지를 다룬다.

## 22단계 — 로컬 노트북에서 직접 돌려보기

빌드용 main과 별개로, 이 노트북에서 바로 돌릴 수 있는 dev 환경이 필요했다 — 새 Supabase 프로젝트(`annswieteom-dev`)와 로컬 Ollama(`qwen2.5:3b-instruct`)를 쓰도록 `.env`만 분리하고, `.env.example`/`config.py`의 공유 기본값은 절대 건드리지 않기로 했다(자세한 건 [00_shared/04_local_dev_environment.md](../checklists/00_shared/04_local_dev_environment.md)). 이렇게 분리해두고 나서야, "로컬에서 직접 인터뷰를 진행해보면 뭐가 걸리는지" 실사용 테스트를 할 수 있었고, 그 결과가 아래 22~25단계다.

## 23단계 — velog 목록 페이지를 열어보면

velog 블로그 URL을 붙여넣는 기능은 이미 있었는데, `/@아이디/posts` 같은 "게시물 목록" 페이지를 넣으면 개별 글이 아니라며 거부하고 있었다. 그런데 실제로 이 주소를 써보니 — 비공개 게시물이 하나라도 섞여 있으면 "비공개라 못 가져온다"는 오해의 소지가 있는 메시지가 나오고 있었다(공개 게시물까지 다 같이 거부되는 것처럼 보임). 요청받은 개선 방향은 "거부하지 말고, 그 목록 페이지에서 공백 기간에 해당하는 글을 전부 가져오자"였다.

velog의 공개 GraphQL 엔드포인트(`v3.velog.io/graphql`)를 실제로 introspection까지 해가며 `posts(input: GetPostsInput!)` 쿼리가 커서 기반 페이지네이션을 지원한다는 걸 확인하고, 최신순으로 페이지를 넘기다가 공백 시작일보다 오래된 글이 나오면 멈추는 방식으로 구현했다. `POST /sessions/{id}/records`의 응답이 단일 객체에서 배열로 바뀌었다 — 일반 글 하나를 넣어도 이제 원소 1개짜리 배열이 온다.

실제 계정(`sjyoon1101`, 실제 글 11개)으로 라이브 테스트하다가 전혀 다른 문제를 하나 더 발견했다: 로컬 Ollama에 임베딩 모델(`bge-m3`)이 한 번도 받아진 적이 없어서, 모든 기록물이 임베딩 단계에서 조용히 실패하고 있었다(Gemini로 폴백되면서 벡터 차원이 안 맞아 다시 실패). `ollama pull bge-m3`로 받고 나니 11개 전부 정상 처리됐다.

## 24단계 — 같은 질문이 네 번 반복되던 이유

로컬에서 인터뷰를 직접 진행하다가 "질문에 답해도 다음 단계로 안 넘어간다"는 걸 직접 겪었다. 재현해보니 원인은 명확했다 — 카테고리별 고정 질문은 "확인된 사실 중에 이 질문의 fact_type이 있는가"로 다음 질문을 정하는데, 로컬의 작은 모델(3B)이 가끔 엉뚱한 fact_type을 답으로 내놓았다(예: "힘들었던 점" 질문인데 이전 질문의 타입인 "공부 목표"로 답을 라벨링). 그러면 서버 입장에서는 "이 질문 아직 답 안 됐네"가 되어 같은 질문을 무한 반복하게 된다. 고쳐 쓴 방식은 간단했다 — AI가 뭐라고 답하든, fact_type은 서버가 원래 물어본 질문의 타입으로 강제 고정한다. AI의 자유도를 하나 줄이는 대신, 진행이 항상 보장된다.

같은 세션에서 "공부, 공모전, 알바"처럼 쉼표로 나열한 짧은 입력이 카테고리로 전혀 인식되지 않는 것도 재현됐다 — 같은 입력을 5번 돌려보니 3번은 빈 배열이 나왔다. 완전한 문장이 아니라 단어 나열이면 작은 모델이 곧잘 포기해버리는 경향이 있어서, 프롬프트에 정확히 이 형태의 입력 예시를 하나 박아 넣어 성공률을 높였다(완전히 없앨 수 있는 종류의 문제는 아니다).

## 25단계 — 질문을 더 똑똑하게, 그리고 더 적게

다음 요청은 인터뷰를 더 "대화답게" 만드는 것이었다 — 지금은 카테고리마다 고정 질문 4개를 순서대로 다 물어본 뒤에야 AI가 답변 맥락을 반영한 후속 질문을 시작하는데, 그래서 "기획과 개발을 담당했어요"처럼 두 가지를 뭉뚱그린 답이 나와도 바로 파고들지 않고 전혀 다른 다음 고정 질문으로 넘어가버렸다. 답변마다 AI가 그 자리에서 파고들지 판단하도록 바꿨다 — `judge_drilldown`이라는 새 LLM 호출을 추가해서, 고정 질문 사이사이에도 필요하면 AI가 즉석에서 더 구체적인 질문(예: "기획 쪽에서는 구체적으로 어떤 아이디어를 내셨나요?")을 끼워 넣을 수 있게 했다. 실제 로컬 모델로 이 흐름이 그대로 재현되는 것까지 확인했다.

곧이어 "카테고리당 질문 횟수를 3회까지로 줄이자"는 요청이 왔다 — 총 질문 수(고정+AI 합산) 상한을 3으로 낮췄다. 질문뱅크 자체는 카테고리마다 4개를 그대로 정의해두지만, 실제로는 최대 3개만 쓰이고, AI가 중간에 파고들기를 한 번이라도 쓰면 그만큼 고정 질문 자리를 대신 차지한다 — 예산이 빠듯해질수록 "지금 파고들지, 다음으로 넘어갈지" 판단의 비중이 커지는 구조다. `ActivityCategory.questions_asked` 컬럼을 새로 추가해 실제 던진 질문 수를 추적한다.

## 26단계 — 프로덕션에서 게스트 세션이 두 개가 되는 이유

로컬 작업 중간에 프로덕션에서 두 가지 신고가 들어왔다 — "게스트 세션이 두 개가 된다"와 "대화가 굳어버린다". 실제 프로덕션 백엔드(`annswieteom.onrender.com`)에 직접 요청을 보내 쿠키/CORS 메커니즘 자체를 확인했는데, 게스트 로그인이 발급하는 리프레시 쿠키도, CORS 설정도 전부 정상이었다.

문제는 다른 곳에 있었다 — `LoadingNotice` 컴포넌트에는 이미 "Render 무료 플랜은 깨어나는 데 최대 1분 걸릴 수 있다"는 주석이 있었는데, 정작 로그인 상태 확인(`/auth/refresh`)과 세션/목록 조회에 걸어둔 타임아웃은 15초였다. 콜드 스타트가 15초~1분 사이에 걸리면, 실제로는 멀쩡한 쿠키를 갖고 있어도 클라이언트가 먼저 포기하고 "로그아웃 상태"로 처리해버린다. 그러면 홈 화면엔 "게스트로 시작하기" 버튼이 다시 뜨고, 이걸 누르면 완전히 새로운 게스트 계정과 세션이 생기면서 기존 것과의 연결이 끊긴다. 세 곳의 타임아웃을 전부 65초로 올렸다 — 코드가 이미 스스로 문서화해둔 "최대 1분"이라는 약속과 실제 강제값이 어긋나 있던 경우였다.
