# 56. 프로필 초기화 기능 + "맞춤 정보" 어휘 통일 (2026-09-17)

사용자 요청: "프로필 초기화 기능 / 맞춤 정보 수정 어휘 통일". 코드 감사 결과
두 요구 모두 실제 결함(초기화 수단 전무, `/archive` 페이지 안에서 같은 이름이
서로 다른 두 대상을 가리킴)이었다.

## 무엇을

### 1. 프로필 초기화 기능 (신규)

기존엔 `user_attributes`를 한 번에 지우는 수단이 전혀 없었다 — 있는 건
개별 삭제(`DELETE /me/attributes/{id}`, 값 하나씩)와 민감정보 동의 철회
(`PUT /me/consents/sensitive-profiling`, 민감정보만) 둘뿐이었다.

- 신규 서비스 함수 `attrs.reset_all_attributes(db, user_id) -> int` —
  `DELETE FROM user_attributes WHERE user_id = ...` 한 줄로 **민감정보
  포함 전부**를 지운다. 개별 삭제는 같은 값의 재추정을 막으려고 `rejected`
  상태로 행을 남기지만, 초기화는 "완전히 새로 시작"이 목적이라 그 기억까지
  포함해 행 자체를 지운다 — 이후 대화에서 같은 내용을 다시 말하면 다시
  저장될 수 있어야 "초기화"라는 이름에 맞는다고 판단했다.
- 동의(`user_consents.sensitive_profiling`) 자체는 건드리지 않는다 —
  데이터만 비우고 동의는 유지되는 상태도 정상이다(동의 직후 아직 아무것도
  안 말한 시점과 같은 모양). 동의까지 철회하려면 기존 "동의 철회" 버튼을
  따로 쓰면 된다.
- 신규 `POST /me/attributes/reset` — `AttributesResetRead{reset_count}`를
  돌려줘 "N개를 초기화했어요" 같은 확인을 보여줄 수 있게 했다.
- 프론트: `ProfileAttributesEditor`(민감정보 카드까지 포함하는, "알게 된
  정보"를 다루는 유일한 카드) 헤더에 "프로필 초기화" 버튼 추가 — 지울 게
  있을 때만(`groups.length > 0`) 보이고, `window.confirm`으로 한 번 더
  확인한다(다른 파괴적 액션들과 같은 패턴).

### 2. "맞춤 정보" 어휘 통일

`/archive` 페이지 안에서 "맞춤 정보"가 세 가지 다른 크기로 겹쳐 쓰이고
있었다: (a) 페이지 전체(nav 링크·홈 CTA·`<h1>`), (b) `PreferenceEditor`의
`<h2>`(실제로는 `wish_text` 자유 입력칸 하나만), 그리고 그 옆 카드
`ProfileAttributesEditor`는 아예 다른 말("나에 대해 알게 된 정보")을 썼다.
한 페이지를 위에서 아래로 읽으면 "맞춤 정보"(제목) → "맞춤 정보"(희망사항
카드) → "나에 대해 알게 된 정보"(속성 카드) → "문답 기록"으로, 같은 말이
두 번 겹치고 인접한 두 카드는 서로 무관해 보이는 이름을 썼다. nav 라벨이
"내 문답 기록"에서 "맞춤 정보"로 한 번 바뀐 이력, 홈 CTA를 따로 또 붙인
이력(둘 다 기존 주석에 남아 있음)도 이 페이지 어휘가 이미 한 번 이상
사용자 혼란으로 지적됐었다는 신호다.

- 페이지 레벨(nav·홈 CTA·`<h1>`)의 "맞춤 정보"는 셋이 이미 서로 일치하고
  발견성 문제로 의도적으로 다듬어진 이력이 있어 **그대로 뒀다**.
- `PreferenceEditor`의 `<h2>`/`aria-label`을 "맞춤 정보" → **"직접 적은
  희망사항"**으로 바꿨다 — 내용(자유 입력 희망사항)과 정확히 맞고, 페이지
  제목과 더 이상 겹치지 않는다.
- `ProfileAttributesEditor`의 `<h2>`를 "나에 대해 알게 된 정보" →
  **"대화에서 알게 된 정보"**로 다듬었다 — "직접 적은 희망사항"과 [출처]+
  [정보] 형태로 짝을 이뤄, 페이지 안에서 두 카드가 "직접 vs 대화로"라는
  하나의 축으로 대비된다는 게 바로 읽힌다.
- 코드 주석(`PreferenceEditor.tsx` 상단 docstring)에 이 대비 구조와 변경
  이유를 남겨, 다음에 또 이름이 흔들리지 않게 했다.

  즉시 되돌리고, 새 워크트리(`../Annswieteom-profile-reset`)를 만들어
  거기서 다시 작업했다. 공유 디렉터리엔 흔적이 남지 않았다.
- 초기화 후 DB에 정말 행이 안 남는지(개별 삭제의 `rejected` 잔존과
  구분하기 위해) 확인하려고 `session_client.session_local()`로 직접
  카운트 쿼리를 도는 테스트를 추가했다 — API 응답만으로는(활성 속성만
  보여주므로) 이 차이가 드러나지 않는다.
