# 맞춤 정보 직접 수정 — 인터뷰를 안 해도 정렬을 조종할 수 있게

관련 spec: [main_page_feed.md](../../specs/main_page_feed.md)
날짜: 2026-09-10
선행 작업: [28_typing_indicator_and_activity_probe.md](28_typing_indicator_and_activity_probe.md)

## 배경

사용자 요청: "사이트에서 수집한 개인 정보를 수정할 수 있는 기능도 있어야 할 것 같아. 로그인 이후에 해당 위치에 맞춤 정보 수정 이런 버튼이 있어야하지 싶어."

조사해보니 `/archive` 페이지(헤더의 "내 문답 기록")가 이미 있고 **조회·삭제만** 됐다. 그리고 더 큰 문제가 있었다 — 맞춤 공고 정렬은 `interview_answers`에서만 만들어져서, **공백기 정리를 아직 안 한 사용자는 정렬을 조종할 수단이 아예 없었다.** 결과가 마음에 안 들어도 인터뷰를 처음부터 하는 것 말고는 방법이 없었다.

사용자와 상의해 **기존 답변 수정이 아니라 희망사항 자유 입력**을 넣기로 했다. 답변 원문을 고치는 것보다 "지금 뭘 찾고 있는지"를 직접 쓰는 쪽이 정렬 조종이라는 목적에 맞고, 인터뷰를 안 한 사용자에게도 바로 쓸모가 있다.

## 완료 항목

- `user_preferences` 테이블 + 마이그레이션 `f3b6d0c8a114`(downgrade 왕복 확인).
- `GET/PUT /me/preferences` — `api/profile.py`에 추가. 게스트는 기존 `_require_registered`대로 403.
- `profile_adapter`가 희망사항을 프로필 텍스트 **맨 앞에** 합친다. `has_profile_input()` 신규 — 라우터가 문답 개수가 아니라 "재료가 하나라도 있는가"로 판단한다.
- `PreferenceEditor.tsx` + `/archive` 페이지에 배치, 페이지 제목을 "맞춤 정보"로.
- 진입점 셋: 헤더 링크 이름 변경, 맞춤 공고 섹션 헤더의 "맞춤 정보 수정 →", 그리고 **로그아웃 방문자용 가입 유도 섹션**.
- 테스트 11개 신규(`test_preferences.py`), 전체 **354 passed**.

## 핵심 결정 사항과 이유

**`user_profile_embeddings`에 컬럼을 얹지 않고 테이블을 나눴다.** 그쪽은 언제든 `TRUNCATE` 해도 지문 메커니즘이 다시 채우는 파생 캐시라고 스스로 문서화해뒀는데, 희망사항은 사용자가 직접 타이핑한 원본이라 지우면 복구가 안 된다. 수명이 다른 데이터를 한 테이블에 두면 캐시를 초기화하는 순간 원본이 같이 날아간다.

**희망사항을 프로필 텍스트 맨 앞에 둔다.** 4000자 상한에 걸려 잘려 나가면 안 되고, 사용자가 방금 직접 쓴 말이라 과거 문답보다 현재 의도를 잘 나타낸다. 테스트로 순서를 고정해뒀다.

**라우터의 게이트를 "문답 개수"에서 "재료 유무"로 바꿨다.** 이게 이 기능의 성패다 — 예전 로직을 그대로 뒀다면 희망사항만 적은 사용자는 `answer_count == 0`이라 영영 `no_profile`로 남았을 것이다. 그런데 그게 바로 이 기능이 필요한 사람이다.

**저장 시점에 임베딩을 다시 계산하지 않는다.** 로컬 Ollama 호출이 수 초씩 걸려 저장 버튼이 그만큼 멈춰 보인다. 다음 맞춤 공고 조회가 지문 변화를 감지해 백그라운드로 갱신한다(항목 수집과 같은 stale-while-revalidate). 대신 저장 직후 "맞춤 공고는 다음에 보실 때 반영돼요"라고 적어 뒀다 — 바로 안 바뀌는 걸 침묵으로 두면 저장이 안 된 줄 안다.

**지문 비교에 희망사항을 명시적으로 넣어야 했다.** `profile_needs_refresh`는 문답 개수와 최신 시각만 봤는데, 희망사항만 고치면 둘 다 그대로다. 저장해둔 `profile_text`와 직접 비교하지 않으면 "맞춤 정보 수정"을 눌러도 아무 일도 안 일어난다.

## 트러블슈팅

| 증상 | 원인 | 해결 |
|---|---|---|
| `react-hooks/set-state-in-effect` lint 오류 | 서버 값을 `useEffect`로 초안 state에 동기화 | 파생값으로 바꿈(`draft ?? data?.wish_text ?? ""`). effect로 setState하면 렌더를 한 번 더 태우기도 한다 |
| **프로덕션 로그에 `duplicate key value violates unique constraint "feed_item_embeddings_pkey"`** | 이번 작업과 무관한 **기존 버그**. 수집 락은 `source_key` 단위인데 `_embed_pending`은 "벡터 없는 항목" **전역** 목록을 집는다 — 서로 다른 소스를 갱신하는 두 요청이 동시에 돌면 같은 행을 둘 다 INSERT 한다 | 임베딩 단계를 `asyncio.Lock`으로 직렬화(로컬 Ollama가 어차피 직렬 처리라 잃는 게 없다) + 커밋에서 `IntegrityError`를 관대하게 처리(프로세스가 둘이면 락으로도 못 막는다). 동시 `refresh_feed` 2개로 재현·확인 |

## e2e를 두고 헛짚은 기록

작업 막바지에 e2e가 3~5개씩 실패했다. **"로컬 dev DB가 시드니 리전이라 요청당
2초가 걸려 Playwright 기본 5초 타임아웃을 넘긴다"고 진단하고 사용자에게 그렇게
보고했는데, 틀렸다.**

실제 원인은 훨씬 단순했다 — 작업 중 여러 번 서버를 죽이고 띄우면서 **Next dev
서버가 죽은 채로 테스트를 돌리고 있었다**(`net::ERR_CONNECTION_REFUSED`). 포트가
3000/3001/3002를 오갔고, 한 번은 **경합 수정 전 코드의 백엔드**가 계속 떠 있기도
했다. 포트를 고정하고 두 서버가 실제로 응답하는 걸 확인한 뒤 돌리니 8/9가
통과했다.

교훈: 실패를 보고 원인을 추론하기 전에 **환경이 내가 생각하는 상태인지 먼저
확인해야 한다.** `curl`로 두 서버를 찍어보는 10초를 아끼려다 몇 번의 오진과
잘못된 보고를 했다.

다만 지연 자체는 실재한다(`POST /sessions` 단독 2.0초, `/health` 0.2초 — 실측).
남은 1개 실패는 진짜 그것 때문이었다: 마지막 단언이 인라인 10초였는데 그 테스트만
단독으로 돌려도 27초가 걸린다. 전역 expect 타임아웃(5초 -> 15초)과 테스트
타임아웃(30초 -> 60초)을 올리고, 그 단언의 인라인 값도 25초로 맞췄다.

## 남은 작업

- 맞춤 정보를 반영한 정렬이 실제로 달라지는지는 **로컬 3b가 아니라 운영 모델/실 데이터로** 봐야 의미가 있다. 벡터 자체는 bge-m3로 같지만, 확인은 프로덕션에서.
- 피드 조회가 순차 쿼리 5번을 돈다(비었는지·stale인지·개수·목록·마지막 갱신). 프로덕션 1.3초로 당장 급하진 않지만, 줄일 여지가 있다.
- 기존 문답 답변 원문 수정은 이번 범위 밖이다(사용자 선택). 필요해지면 `PATCH /me/answers/{id}`를 같은 자리에 붙이면 된다.
