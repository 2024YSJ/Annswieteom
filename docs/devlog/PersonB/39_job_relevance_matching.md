# 39. 취업정보 개인화 정확도 수정 — 직무/지역 관련성 (2026-09-13)

사용자 리포트: 희망 지역=경기, 희망 직무=프로그래머로 설정해도 랜딩 "맞춤 공고"와
대화형 검색 둘 다 지역만 대충 맞고 직무는 무관한 공고가 나온다. 탐색 에이전트 4개
(사이트 카피 전수조사는 별도 PR #70)로 원인을 특정한 결과, **두 개의 독립된 하위
시스템에 각각 다른 원인의 실재 버그**가 있었다.

## 원인

### 랜딩 피드 (`/feed/jobs/recommended`)

`services/feed/matching.py`의 `MatchProfile`에는 애초에 `desired_job` 필드가 없었다 —
`user_attributes`에 저장은 되지만 매칭에 절대 안 쓰였다. 이 엔드포인트는
`profile_adapter.py`의 `read_profile_signal`(면접 답변 + `wish_text` 통짜 텍스트를
임베딩한 벡터)만으로 코사인 유사도 정렬했고, 지역조차 구조화된 하드 필터가 아니라
벡터 유사도에 묻힌 약한 신호였다 — 정책·훈련과정 섹션은 `matching.py`의 구조화 지역
매칭을 쓰는데 구인공고만 안 썼다.

### 대화형 검색 (`job_search.py` + `job_info_client.py`)

`user_attributes`는 대화형 검색에서 아예 읽히지 않았다 — 오직 그 턴의 채팅 메시지
텍스트만 LLM으로 파싱했다. 파싱에 성공해도 `_FILTERABLE_CATEGORIES`가
`training_course` 하나만 포함해서, 6개 카테고리 중 5개(채용행사/공채속보/
공채기업정보/구직자프로그램/강소기업)는 지역·직무 파라미터를 고용24에 아예 안
보내고 매번 같은 전국 무필터 상위 20건을 받아왔다. 지역이 "그나마 맞는 것처럼"
보인 건 실제 필터가 아니라 무필터 전국 덤프에서 인구가 많은 경기/인천이 통계적으로
많이 뽑히는 우연이었다.

**라이브 API 실측(읽기 전용 GET, 2026-09-13)**: 지역 9개·직무 8~9개 후보 파라미터명을
5개 wk/* 엔드포인트에 전부 시도한 결과:

| 카테고리 | 지역 파라미터 | 직무 파라미터 |
|---|---|---|
| `job_fair`(채용행사) | 없음 | **`keyword`(자유텍스트, eventNm 부분일치)** |
| `promising_sme`(강소기업) | **`region=<광역2자리>000`(5자리, 예 41000=경기)** | 없음 |
| `public_recruitment`/`public_recruitment_company` | 없음 | 없음 |
| `job_seeker_program` | 미확인(그날 피드 자체가 0건) | 미확인 |

## 완료

**랜딩 피드**: `MatchProfile.desired_job` 추가, `load_match_profile`이 채워 넣음.
`matching.py`에 `occupation_score`(제목/부제/메타 텍스트 부분일치·토큰겹침, 훈련과정
`srchTraProcessNm`과 같은 단순함)·`job_region_hit`(구인공고는 eligibility에 지역
코드가 없어 텍스트 부분일치로 대체)·`rank_jobs_by_profile`(직무 겹침 → 지역 겹침 →
벡터 유사도 → 최신순) 신설. `/feed/jobs/recommended`는 `desired_job`/구조화 지역이
있을 때만 이 경로를 타고, 없으면 기존 벡터 전용 경로 그대로 — 회귀 없음
(`no_profile`/`preparing` 폴백 계약 유지).

**대화형 검색**: `_FILTERABLE_CATEGORIES`에 `job_fair`(`keyword`)·`promising_sme`
(`region=<code>000`) 추가 — 실측으로 확인된 두 파라미터만 연결. 메시지에 조건이
없으면(`extract_job_info_query_params`가 빈 결과) 로그인 사용자(게스트 제외)의 저장된
`desired_region`/`desired_job`으로 대체 — 스펙 로드맵의 미구현 항목("저장된 희망
지역·직무로 검색 조건 프리필")을 채웠다. 필터를 못 건 3개 카테고리는 조회 개수를
20→30(`_UNFILTERED_FETCH_LIMIT`)으로 늘려 사후 LLM 관련성 판정의 후보 풀만 넓혔다.

**검증**: pytest 477개 전부 통과(신규 11개 포함). 브라우저 에이전트로 실측 —
- 랜딩 피드: 오늘 캐시에 "프로그래머" 문자열이 든 공고가 0건이라(데이터 가용성
  문제, 버그 아님) desired_job을 임시로 "소프트웨어"(캐시에 14건 존재)로 바꿔
  재현 — 14건 전부 1~14위로 올라오고 `matched_labels`에 "희망직무 소프트웨어 관련"
  "경기 관련"이 정확히 붙음, 무관 공고는 뒤로 밀림. 프로필 없는 계정은 여전히
  `fallback_reason: "no_profile"`로 정상 동작(회귀 없음).
- 대화형 검색: "요즘 뽑는 데 있어?"(조건 없음) → 프로필에서 `keyword=프로그래머`
  자동 채움 확인. "부산 조리사 채용 있어?"(명시 조건) → 메시지 자체 조건(부산/요리)이
  저장된 프로필을 덮어쓰지 않고 그대로 쓰임 확인.

## 핵심 결정과 이유

**직무 매칭을 고용24 API가 아니라 로컬 텍스트 매칭으로 구현했다.** 강소기업 등
구인공고 4개 카테고리는 서버 측 직무 필터가 없다는 게 실측으로 확인됐다 —
`training_course`처럼 서버에 보낼 수 없으므로, 이미 캐시된 `FeedItem` 제목/부제
텍스트에 대해 로컬로 부분일치·토큰겹침만 본다. NLP 유사도 매칭은 안 한다 —
이 프로젝트의 기존 단순함 기조(훈련과정의 `srchTraProcessNm`도 순수 부분일치)를
따랐다.

**프로필 프리필은 게스트를 제외한다.** `/feed/jobs/recommended`는 게스트도
개인화하는데(신호가 조금이라도 있으면 이득이고 공개 공고만 돌려주므로) 대화형 검색의
프리필은 로그인 사용자만 대상으로 했다 — 게스트는 애초에 저장된 구조화 속성이 없어
실질적 차이는 없지만, 정책이 완전히 통일돼 있진 않다. 사소한 불일치라 지금은 두고,
필요해지면 통일한다.

**관련성 판정 프롬프트에 프로필 힌트를 넣는 건 이번엔 안 했다.** 계획에 "여유 되면"
선택 항목으로 남겨뒀던 것 — `LLMProvider` 프로토콜 표면을 넓히는 변경이라 범위를
좁게 유지했다. 다음에 이 영역을 다시 볼 때 같이 본다.

**공채속보/공채기업정보/구직자프로그램의 진짜 필터는 이번에도 못 찾았다.** 지역
9개·직무 8~9개 후보를 두 엔드포인트에 전부 시도해도 무효과였고, 구직자프로그램은
그날 피드 자체가 0건이라 검증이 원천적으로 불가능했다. 후보 풀 확대(20→30)로
완화만 하고, 나중에 데이터가 쌓이거나 고용24 문서가 갱신되면 재실측한다.
