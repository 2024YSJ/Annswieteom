# LLM 샘플링·컨텍스트·few-shot 하네스 결함 3건 + 사이드바 줄바꿈

관련 spec: 없음(16~18과 동일하게 체크리스트 밖 항목)
날짜: 2026-09-09

---

## 배경

두 가지 보고가 함께 들어왔다.

1. 사이드바 그룹 헤더에서 "한 줄로 쓸 수 있는 문장이 두 줄이 되어 있다".
2. 취업 정보 검색의 답변 품질이 좋지 않다 — **이게 하네스 문제인지 모델 성능 문제인지 판별**해달라.

2번은 [devlog 18](18_llm_relevance_instead_of_keyword_matching.md)이 "남은 작업"으로 남겨둔 질문과 같은 것이다. 그때는 로컬 3b 모델로 눌러봤을 때 관련성 판단이 들쭉날쭉했는데, 그게 LLM 판단 방식 자체의 문제인지 약한 dev 모델 탓인지 결론을 못 냈다.

## 결론부터

**하네스에 실제 결함이 3건 있었고, 그게 품질 저하에 실측으로 기여하고 있었다.** 순수 모델 문제로 볼 수 없었다. 다만 결함을 다 고친 뒤에도 held-out 사례에서 누락이 남아, 그 잔여 격차는 모델 용량 쪽으로 보인다 — 이건 72b/Gemini 대조가 있어야 확정된다(아직 못 함, 아래 "남은 작업").

## 완료 항목

### 결함 1 — 온도(sampling) 미설정 → 같은 입력에 다른 답

`local_ollama._generate`와 `gemini_provider._call`의 요청 본문에 `temperature`가 아예 없어서, 분류·판단처럼 결정적이어야 하는 호출에 모델 기본값(~0.7)이 그대로 걸려 있었다.

**실측(고정 후보 6건, devlog 18의 회귀 질의, 5회 반복):**

| | 결과 | 서로 다른 결과 |
|---|---|---|
| 수정 전 | `[1,2,5]` 3회 / `[1]` 2회 | **2종 / 5회** |
| 수정 후 | `[1,2,5]` 5회 | 1종 / 5회 |

즉 "들쭉날쭉하다"는 관찰의 상당 부분은 모델 능력이 아니라 **샘플링 노이즈**였다. 이건 모델을 14b/72b로 바꿔도 그대로 남았을 문제다.

**설계**: 공용 private 헬퍼에 `temperature`를 키워드 전용 필수 인자로 넣고, 12개 호출 지점이 `base.py`의 `TEMPERATURE_DETERMINISTIC`(0.0) / `TEMPERATURE_CREATIVE`(0.7) 중 하나를 명시적으로 고르게 했다. 판단 8개(`classify_job_info_query`, `select_relevant_job_info_results`, `extract_period`, `extract_categories`, `extract_activity_items`, `extract_facts`, `judge_sufficiency`, `judge_drilldown`) / 생성 4개(`draft_answer`, `followup_question`, `generate_document`, `draft_job_info_query_from_facts`).

`extract_facts`를 판단 쪽에 넣은 건 의도적이다 — 정직성 가드레일에 인접한 호출이라, 추출된 사실은 사용자가 말한 것을 그대로 반영해야 하고 여기서의 표현 다양성은 개선이 아니라 윤색 위험이다.

**기본값을 두지 않은 이유**: 고치려던 문제가 바로 "암묵성"이었다. 전역 기본값 + 개별 오버라이드로 하면 생성 계열 4곳의 동작이 조용히 바뀌고, 새 메서드를 추가하는 사람이 오버라이드를 잊는 순간 같은 버그가 재발한다. 지금 구조는 새 메서드를 추가할 때 "판단인가 생성인가"를 한 번 결정하도록 강제한다. `TEMPERATURE_CREATIVE = 0.7`은 대부분 모델 기본값에 맞춘 값이라, 이번 변경으로 생성 계열의 동작은 바뀌지 않는다(하향 튜닝은 독립적으로 측정할 별건).

`LLMProvider` Protocol과 `fallback.py`, `FakeLLMProvider`는 건드리지 않았다 — 샘플링은 능력 계약이 아니라 구현 방식이라서다. 덕분에 기존 테스트는 한 줄도 수정하지 않았다.

### 결함 3 — `num_ctx` 미설정 (먼저 적용)

`options` 키 자체가 없어서 Ollama 런타임 기본 컨텍스트가 걸렸다. 모델이 지원하는 32k와 무관하게 그보다 훨씬 작은 값이고, 넘치면 **에러 없이 조용히 잘린다** — 규칙 블록이나 후보 목록 앞부분이 사라진 채 판단이 이뤄질 수 있다. 훈련과정은 엔드포인트 4개×10건으로 후보가 40건까지 간다.

`_NUM_CTX = 8192`을 `local_ollama.py`에만 두고 전 호출 공통으로 고정했다. 호출마다 값을 바꾸면 Ollama가 `num_ctx`별로 런너를 잡아 모델을 매번 재적재하므로, VRAM을 조금 아끼려다 지연을 크게 잃는다. Gemini는 대응 노브가 없고 컨텍스트가 충분히 커서 손대지 않았다 — 그래서 이 상수는 공용 시그니처로 넘기지 않는다.

**방어선은 후보 개수가 아니라 줄 길이로 걸었다.** 개수를 자르면 devlog 18이 고친 버그(뒤쪽 2개 엔드포인트 결과가 통째로 버려지던 것)를 되살린다. 대신 템플릿에서 필드별 `truncate`를 적용했다. 실제 폭탄은 `public_recruitment_company`였다 — `job_info_client.py`가 회사 소개 자유텍스트(`coIntroSummaryCont`)를 `meta_lines`에 그대로 담고 이게 20건 반복된다. 템플릿 전용 변경이라 프론트로 가는 `JobInfoResultRead`는 영향이 없다.

덤으로 후보 루프의 빈 줄도 없앴다(`trim_blocks` 미설정으로 항목마다 빈 줄이 들어가 줄 수가 배였다). 최악 케이스(40건 + 2000자 meta 1건) 렌더 결과는 **5,456자**로, 절단·단일 간격·`[출력 형식]` 생존 모두 확인했다.

### 결함 2 — few-shot 예시 누락 (마지막 적용)

`select_relevant_job_info_results.jinja`에는 규칙만 있고 worked example이 없었다. 더 쉬운 작업인 `classify_job_info_query.jinja`에는 예시가 2개 있는데, 더 어려운 작업(N개 후보 중 인덱스 부분집합 고르기)에 없었다.

실제 렌더 형식과 정확히 같은 모양의 예시 2개를 넣었다 — 예시 1은 `job_fair` 형태(단일 선택), 예시 2는 `training_course` 형태(복수 선택). 포함 사유(표현이 달라도 의미가 맞는 경우: ICT↔IT, 자바 웹 개발↔백엔드)와 제외 사유(직무는 맞지만 지역이 틀린 경우 ← 규칙이 암시만 하고 시연하지 않던 어려운 제외)를 `(판단)` 줄로 보여주고 `출력:` JSON으로 끝맺는다.

**여기서 과교정을 한 번 겪었고, 그게 이번 작업에서 가장 배울 게 많은 부분이다.**

처음 넣은 버전은 예시 1을 복수 선택, 예시 2를 단일 선택으로 두고 예시 2 끝에 "관련 있는 게 하나뿐이면 하나만 골라라 — 개수를 늘리려고 애매한 항목을 끼워 넣지 마라"를 붙였다. 약한 모델의 "다 고르기" 편향을 억제하려던 것이었는데, 실측해보니 **반대 방향으로 부러졌다**:

| | 오탐(precision) | 누락(recall) |
|---|---|---|
| few-shot 없음 | 0.67 (`[1,2,5]` — 무관한 5번 포함) | 1.00 |
| few-shot 1차 | 1.00 | **0.50** (정답 2건 중 1건만) |
| few-shot 2차(현재) | 1.00 | 1.00 |

즉 오탐은 잡았지만 정답 2건 중 1건만 고르고 멈췄다. 원인은 (a) 마지막에 본 예시가 단일 선택이었던 recency 효과와 (b) "하나만 골라라"라는 문구, 그리고 (c) **원래 프롬프트에 "억지로 채우지 마라"는 있었지만 "일찍 멈추지 마라"에 해당하는 지시가 아예 없었다**는 것이다. 규칙 블록에 양방향 지시("여러 개면 하나만 고르고 멈추지 말고 전부 골라라, 반대로 애매한 걸 채워 넣지도 마라")를 넣고 예시 순서를 뒤집어 복수 선택이 마지막에 오게 해서 고쳤다.

이 회귀가 조용히 돌아오지 않도록 `test_select_relevant_prompt_demands_exhaustive_selection`을 남겼다 — "전부" 지시와 "마지막 예시가 복수 선택"을 둘 다 검사한다.

### 사이드바 그룹 헤더 줄바꿈

`SessionGroup` 헤더 행이 구조적으로 넘칠 수밖에 없는 상태였다. `.app-sidebar`는 220px 고정에 패딩 16px씩이라 콘텐츠 폭이 188px인데, 헤더 행에 `gap`이 없고(`justifyContent: space-between`만), 타이틀에 `flex:1`/`minWidth:0`/`whiteSpace:nowrap`이, 버튼에 `flexShrink:0`이 전혀 없었다. 게다가 버튼 라벨이 타이틀을 그대로 중복해서(`공백기 채우기` + `+ 공백기 채우기` + 버튼 패딩 ≈ 200px) 합산 폭이 항상 컨테이너를 넘었고, 한글은 글자마다 줄바꿈 기회가 있어 눌린 `<h2>`가 두 줄로 접혔다.

바로 위 `SessionRow`는 이미 올바른 패턴(`gap:4` + `flex:1, minWidth:0` + `whiteSpace:nowrap`/ellipsis + `flexShrink:0`)을 갖고 있었다 — 헤더만 그 처리가 빠져 있었다.

**`gap`만 추가하면 문제가 "타이틀 줄바꿈"에서 "버튼 넘침"으로 이동할 뿐**이라, 중복된 버튼 라벨을 `+` 하나로 줄이고 전체 의미는 `title`/`aria-label`로 넘겼다. 그룹 타이틀이 바로 위에서 무엇을 만드는지 이미 설명하므로 정보 손실은 없다. 호출부의 `newLabel`도 `"+ 공백기 채우기"` → `"공백기 채우기 새로 만들기"`로 바꿨다(aria-label에 "+"가 읽히는 걸 피함). `guest.spec.ts`가 이 버튼을 옛 라벨로 클릭하고 있어서 셀렉터도 같이 고쳤다.

실제 브라우저 측정: 데스크톱 220px과 모바일 드로어 280px 양쪽에서 두 타이틀 모두 **1줄**(높이 20px / 줄높이 17px), 말줄임 불필요, 버튼 넘침 0px.

## 트러블슈팅

**Turbopack 빌드가 안 된다(환경 문제, 코드와 무관).** `next build`가 `Turbopack is not supported on this platform`으로 실패한다. 원인은 Application Control 정책이 `@next/swc-win32-x64-msvc/next-swc.win32-x64-msvc.node`를 차단해서 네이티브 바인딩 대신 WASM만 로드되는 것이고, Next.js 16의 기본 빌드 경로인 Turbopack은 네이티브 바인딩을 요구한다. `next build --webpack` / `next dev --webpack`으로는 정상 동작한다. devlog 18 시점(하루 전)엔 빌드가 됐으니 정책이 최근에 바뀐 쪽으로 보인다 — 배포 전에 정리 필요.

**e2e를 병렬로 돌리면 인증 계열이 깨진다.** 기본 4워커로 돌리면 8개 중 4개가 실패하는데, 실패 지점이 전부 랜딩 페이지 선택 버튼이고 백엔드 로그엔 `register 201` 직후 `login 401`, `register 409`가 남는다. 원격 dev Supabase에 병렬로 붙을 때의 경합이다. `--workers=1`로는 8개 전부 통과하고 2회 재현된다. 이번 변경과는 무관하지만, 앞으로 e2e는 직렬로 돌리는 게 맞다.

## 남은 작업

**약한 모델 vs 강한 모델 대조는 아직 못 했다** — 이게 "잔여 격차가 모델 용량 문제"라는 판단을 확정할 유일한 방법이다.

결함 3건을 다 고친 뒤 로컬 3b(`qwen2.5:3b-instruct`)의 상태:

| 사례 | 결과 | precision / recall | 회차 간 분산 |
|---|---|---|---|
| in-prompt (경기북부/백엔드 — 예시와 동일) | `[1, 2]` | 1.00 / 1.00 | 없음 |
| **held-out (대전/간호조무사 — 프롬프트에 없음)** | `[0]` | 1.00 / **0.50** | 없음 |

in-prompt 사례가 만점인 건 train-on-test라 일반화의 증거가 못 된다. held-out 사례에서는 **"전부 골라라" 지시와 복수 선택 예시가 있는데도 정답 2건 중 1건만 고른다**(안정적으로, 매번 같게). 3b가 목록을 끝까지 훑어 조건에 맞는 걸 모두 열거하는 능력이 부족한 것으로 보이지만, 확정하려면 같은 고정 입력으로 72b/Gemini를 돌려봐야 한다.

대조 실험 방법론에서 놓치면 안 되는 것: **워크넷 API는 시점마다 다른 데이터를 주고** `search_training_courses`는 `date.today()`를 창 시작으로 쓴다. 정오의 3b와 오후의 72b를 비교하면 서로 다른 후보 목록을 비교하는 셈이라 아무것도 증명하지 못한다. 그래서 (1) 6개 카테고리 조회 결과를 한 번 덤프해 고정 입력으로 쓰고, (2) 모델 출력을 보기 전에 정답을 라벨링하고, (3) 라우트를 우회해 `/api/chat`에 직접 프롬프트를 넣어 비교해야 한다. `.env`를 터널/72b로 임시 변경하는 건 CLAUDE.md가 허용하는 경우이고, 끝나면 원복하고 `.env.example`/`config.py`는 건드리지 않는다. (72b는 현재 DGX Spark(spark-99ae)에 다운로드 중.)

판정 기준: 3b는 안정적이지만 recall이 낮고 72b는 높다 → 하네스는 고쳐졌고 잔여 격차는 모델 용량(= devlog 18의 미해결 질문에 대한 답). 둘 다 낮다 → LLM 관련성 판단 방식 자체를 더 손봐야 한다(예시 추가, 또는 40건 훈련과정을 엔드포인트별 호출로 분리).

## 고쳤어야 하지만 이번 범위에 넣지 않은 것

- **실패 모드가 구분되지 않는다.** 환각 인덱스가 필터링돼 `[]`가 된 경우와 진짜로 관련 항목이 없어 `[]`인 경우가 응답상 동일하다(의도된 설계지만 진단을 어렵게 한다). 온도 고정으로 최소한 **재현은 가능**해져서 "샘플링 노이즈였나"는 배제할 수 있게 됐다. 나중에 필요하면 최소 add-on은 `job_search.py::_search_category`에 `len(candidates)` vs `len(relevant_indices)` 로그 1줄 + 필터로 버린 인덱스 개수 카운트 — 4줄 정도, 시그니처 변경 없음.
- `{"relevant_indices": "0,2"}`(문자열)는 예외 없이 조용히 `[]`가 된다 — 문자열을 순회하면 글자가 나오고 어느 것도 유효 인덱스가 아니기 때문. 위와 같은 범주라 동작은 그대로 두고 기록만 남긴다(`test_local_ollama.py`에 이 경계가 드러나 있다).
- `_NUM_CTX`를 `config.py` 설정으로 승격: 8192가 3b와 72b 모두에서 동작하므로 지금 이득이 없다.
- `TEMPERATURE_CREATIVE` 하향 튜닝(0.3~0.5): 생성 품질에 영향이 있어 독립적으로 측정해야 한다.
