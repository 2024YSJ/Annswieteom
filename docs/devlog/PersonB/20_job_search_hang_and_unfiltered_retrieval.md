# 일자리 찾기가 멈추는 문제와, 조건 없이 조회하던 문제

관련 spec: 없음(16~19와 동일하게 체크리스트 밖 항목)
날짜: 2026-09-09

---

## 배경

두 가지 보고가 들어왔다.

1. 모델이 적절한 답변을 만들지 못하고 **서비스가 정지**된다.
2. 모델이 **적절한 API를 호출하지 못한다**.

실측해보니 서로 다른 원인이었고, 둘 다 코드 문제였다. 그리고 2번을 고치면 1번의 비용이 함께 내려가는 관계였다.

## 문제 1 — 서비스가 정지되는 이유

`asyncio.gather`로 카테고리별 관련성 판단을 **동시에** 던지고 있었는데, 로컬 Ollama는 요청을 직렬 처리한다(`OLLAMA_NUM_PARALLEL` 미설정). 뒤에 던진 호출들은 큐에서 기다리는 동안 자기 45초 타임아웃을 다 써버린다. 라우트와 동일한 6-way fan-out을 재현한 결과:

```
관련성 판단 1회 (후보 20건)          37.3s     ← 45초 예산에 여유가 거의 없음
6개 동시 (라우트와 동일)
  채용행사              35.1s  성공
  공채속보/공채기업정보/직업훈련과정
  구직자프로그램/강소기업     45.3s  전부 TimeoutError
  전체 벽시계            45.3s
```

여기에 네 가지가 겹쳐 "정지"로 보였다.

**최악 케이스가 기본 케이스였다.** 분류에 사용자의 원 질문("백엔드 개발자, 경기 북부")을 넣으면 6개 카테고리를 **모두** 고른다(측정). 즉 이 질문은 항상 6-way fan-out을 유발했다.

**실패가 조용히 삼켜졌다.** `FallbackProvider`는 `TimeoutError`도 잡으므로 500이 아니라, Gemini 시도(로컬 `.env` 키가 플레이스홀더라 즉시 실패) → `AllProvidersFailedError` → 라우트가 `return None`으로 그 카테고리를 버렸다.

**전부 실패하면 화면에 아무것도 안 나왔다.** `categories=[]` + `clarification_question=None`이면 `JobSearchChatPage`는 사용자 말풍선만 그리고 AI 응답 말풍선을 아예 렌더하지 않는다. 에러도 안내도 없다.

**프론트엔드에 타임아웃이 없었다.** `lib/api/client.ts`에 `AbortController`/timeout이 전혀 없어서, 응답이 안 오면 "관련 정보를 찾고 있어요..."에서 무한 대기했다.

### 고친 것

- 조회(HTTP)는 병렬로 유지하고 **관련성 판단은 순차로** 돌린다. Ollama가 어차피 직렬이라 동시성은 이득이 0이고 큐 타임아웃만 만든다. **fan-out은 싼 쪽에서만 하고 비싼 쪽에서는 하지 않는다** — 기존 코드는 정확히 반대였다.
- 카테고리 상한 3개(`_MAX_CATEGORIES_PER_QUERY`). 분류 프롬프트에 "관련성 높은 순으로" 지시를 넣어 앞에서 자르는 게 의미를 갖게 했다.
- 질문 하나당 전체 시간 예산 90초(`_QUERY_BUDGET_SECONDS`)를 두고, 넘기면 남은 카테고리는 `skipped`로 넘기고 **그때까지 모인 결과만** 돌려준다. `asyncio.timeout`으로 감싸서 취소가 실제로 httpx 요청까지 전파되게 했다.
- 응답에 `skipped_category_labels`를 실어 **무엇이 빠졌는지 알려준다**. 화면에는 "○○ 정보는 이번에 가져오지 못했어요"로 표시하고, 카테고리가 하나도 안 남았으면 안내 말풍선을 반드시 하나 띄운다 — 한 턴에 AI 응답이 0개인 상태를 없앴다.
- 프론트엔드에 `AbortSignal.timeout(105초)`(백엔드 예산 90초보다 길게 — 더 짧으면 서버가 부분 결과를 주기 직전에 끊는다) + 시간 초과 전용 안내 문구 + **"다시 시도" 버튼**(실패한 질문을 붙잡아 둬서 다시 타이핑하지 않아도 되게).

## 문제 2 — "적절한 API를 호출하지 못한다"의 진짜 원인

분류는 생각보다 정확했다(공채→`public_recruitment`, 박람회→`job_fair`, 무관한 질문→`[]`). 원인은 다른 데 있었다: **조회 호출에 검색 조건을 단 하나도 넘기지 않았다.**

6개 카테고리 함수 전부가 `authKey`/`returnType`/`startPage=1`/`display=20`만 보내고(훈련과정은 날짜만 추가), 사용자 질문에서 나온 지역·직무를 전달할 **수단 자체가 없었다**. 그런데 워크넷 API는 필터를 완전히 지원한다:

| 호출 | 상위 결과 |
|---|---|
| 기존 코드(필터 없음) | 강원 홍천, 서울 서초, 경기 고양 … (전국 무작위) |
| `srchTraArea1=41`(경기) | 경기 고양, 파주, 오산 |
| `srchTraProcessNm=자바` | 자바 과정만 |
| 경기 + "개발" | 성남·수원 개발 과정 |
| `srchTraArea2=41280` | 경기 **고양시만** |

즉 엔드포인트는 맞게 고르면서 질의를 실을 방법이 없어서, 전국 무작위 20건을 받아놓고 LLM에게 "여기서 경기 북부 백엔드를 찾아라"라고 시키는 구조였다. 애초에 후보에 없으니 못 찾는 게 정상이고, devlog 18의 "관련성 판단"은 이 검색 실패를 사후에 메우려는 시도였던 셈이다.

### 조건을 실을 때 조심해야 했던 것

**같은 파라미터에 값을 여러 개 넣는 건 불가능하다.** 콤마(`11,41`)는 **0건**, 반복 파라미터(`11`&`41`)는 **첫 값만** 적용된다(둘 다 실측). 그래서 "서울이나 경기"는 호출을 쪼개는 것만이 방법이다. 특히 콤마가 에러가 아니라 0건이라는 게 위험하다 — `_check_error`에 안 걸려서 "그 지역에 정보가 없다"로 잘못 보인다.

**지역 코드는 추측하면 안 된다.** 잘못된 코드도 에러가 아니라 조용한 0건이다. 전부 실호출로 검증했고, 두 가지가 예상과 달랐다:
- 강원은 42가 아니라 **51**, 전북은 45가 아니라 **52**(특별자치도 신 코드). 구 코드는 0건.
- 광주(29)는 두 엔드포인트 모두 0건이었다. 코드가 틀린 건지 해당 기간에 과정이 없는 건지 **구분할 방법이 없다**.
- 경기 북부 시·군 코드 8개(의정부/동두천/고양/구리/남양주/파주/양주/포천)는 해당 시·군만 정확히 돌려줬고, 연천·가평은 0건이었다.

그래서 LLM에게 코드를 외우게 하지 않는다. LLM은 **지역명만** 뽑고(프롬프트에 인식 가능한 어휘 목록을 그대로 보여줘서 그 안에서만 고르게 한다), 코드 변환은 `app/services/job_pipeline/regions.py`의 결정적 테이블이 담당한다. 알 수 없는 지역명은 조용히 건너뛰고 조건 없이 조회한다.

### 고친 것

- 새 LLM 능력 `extract_job_info_query_params(query, known_regions)` → `JobInfoQueryParams(regions=[...], keywords=[...])`. 질문당 **1회** 호출. 같은 차원에 값이 여러 개 올 수 있어 전부 리스트다.
- `regions.py`: 검증된 광역 17개 + 경기 시·군 코드 + 권역("경기 북부"/"경기 남부"/"수도권") 매핑.
- **권역은 시·군 코드로 펼치지 않고 광역 1회 조회 + 주소 후필터링으로 접었다.** 시·군 10개로 펼치면 훈련과정은 엔드포인트가 4개라 호출이 40회가 된다. 후필터링을 하는 호출은 `pageSize`를 30으로 키워서, 경기 첫 10건이 전부 남부일 때 북부가 0건이 되는 걸 막았다.
- 훈련과정 조회는 (지역 × 키워드) 조합마다 호출을 쪼개되 조합 수·지역 수·키워드 수에 상한을 두고, 결과를 합쳐 `(title, subtitle)`로 중복 제거한다.
- **2단 확대(widening)**: 조건을 다 걸어 5건 미만이면 키워드만 떼고 지역만으로 한 번 더 받아 합친다. 그래도 0건이면 조건을 다 뗀다. 지역은 사용자가 명시한 조건이라 마지막까지 유지하는 순서가 맞다.
- 조건을 실을 수 있다고 **확인된 카테고리만** 적용한다(`_FILTERABLE_CATEGORIES = {"training_course"}`) — 남은 5개(wk/* 엔드포인트)의 파라미터 이름은 아직 확인하지 못했고, 확인 없이 추측해 보내면 유효하지 않은 값에 0건이 돌아와 "정보가 없다"로 잘못 보인다.

## 실측 — 문제였던 그 질문으로

질문: `"나는 백엔드 개발자야. 경기 북부에서 일자리를 구하고 싶어."` (로컬 `qwen2.5:3b-instruct`)

| 단계 | 수정 전 | 수정 후 |
|---|---|---|
| 조건 추출 | (없음) | 1.6s → `regions=['경기 북부']`, `keywords=['자바','웹 개발']` |
| 조회 | 0.4s / 28건 (**경기북부 4건**, 부산·전북·충북·경북·대구·강원 섞임) | 0.5s / 10건 (**경기북부 10건**) |
| 관련성 판단 | 13.5~33.9s (회차 변동) → 표시 3건, **경기북부 1건** (충북 청주·경북 포항이 잘못 선택) | 6.7s → 표시 5건, **경기북부 5건** |
| 카테고리 6개일 때 | 1개만 성공, 5개 타임아웃 → 부분/빈 응답 | 상한 3개 + 순차 + 예산, 빠진 건 화면에 표시 |

판단 단계가 후보 28건 → 10건으로 줄면서 지연도 함께 내려갔다. 즉 **조건을 실은 것이 정확도만 아니라 문제 1의 비용까지 같이 해결했다.**

확대 단계를 넣기 전에는 조건이 너무 좁아 2건만 남았다(28건 중 경기북부가 4건이었는데도). 과정명에 "자바"/"웹 개발"이 안 들어간 경기북부 IT 과정이 통째로 빠진 것이라, 정밀도를 조금 내주고 재현율을 되찾는 쪽으로 조정했다.

## 트러블슈팅

**e2e가 6개 실패했는데 원인은 내 코드가 아니었다.** 재실행했더니 프론트 dev 서버가 `EADDRINUSE: :::3000`으로 죽어 있었다 — 앞서 `TaskStop`으로 멈춘 서버가 포트를 계속 잡고 있어서 새 서버가 못 떴고, e2e는 상태가 불분명한 옛 서버를 상대로 돌았다. 점유 프로세스를 정리하고 새로 띄우자 8/8 통과. e2e가 여러 개 동시에 깨지면 **먼저 서버가 살아 있는지** 확인하는 게 맞다.

**테스트 개수가 늘어나는 게 삭제를 가려준다.** 작업 중 `tests/services/test_job_info_client.py`를 새 파일로 착각해 통째로 덮어써서 기존 테스트 9개(5개 카테고리 XML 파싱, 오류 응답 두 형태, 훈련과정 4-엔드포인트 집계/부분 실패)를 지웠다. 그런데 새로 추가한 테스트가 그만큼 많아 전체 개수가 197 → 217로 **늘어났고**, 그래서 전체 통과만 보고는 알아차릴 수 없었다. `git status`에서 그 파일이 신규(`??`)가 아니라 수정(`M`)으로 뜬 걸 보고 발견해 복원했다(그래서 최종 226개). 파일을 새로 만들 때는 개수 증감이 아니라 `git status`의 신규/수정 표시를 봐야 한다.

(19번에 적은 두 환경 문제 — Turbopack 빌드 차단, e2e 병렬 실행 시 인증 경합 — 은 그대로 유효하다.)

## 남은 작업

- **나머지 5개 카테고리에 조건 싣기.** wk/* 엔드포인트의 파라미터 이름을 공식 명세로 확인해야 한다. 지금은 `training_course`만 필터가 걸리고 나머지는 여전히 전국 첫 20건을 받아온다.
- **`_QUERY_BUDGET_SECONDS = 90`은 잠정치다.** 조건이 실려 후보가 줄었으니 실제 소요는 10초 안쪽으로 내려왔다 — 프로덕션 모델로 재측정한 뒤 크게 낮춰야 한다. 90초를 기다려야 하는 사용자는 없어야 한다.
- 광주(29)가 유효한 코드인지 확인. 지금은 0건이면 조건을 풀어 재시도하는 안전망으로 가려져 있다.
- 부정 조건("서울 빼고"), 기간 조건("3개월 이내 시작")은 API에 표현할 파라미터가 없어 사후 필터가 필요하다.
- 조건이 너무 좁아 0건일 때 "조건을 넓혀볼까요?"로 되묻는 대화 처리(지금은 넓힌 결과를 그냥 보여준다).
