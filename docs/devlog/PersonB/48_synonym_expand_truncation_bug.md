# 48. 동의어 확장 truncation 순서 버그 — "유치원교사"가 재배포 후에도 여전히 0건이던 이유 (2026-09-15)

devlog 47에서 "유치원교사"→"보육교사" 동의어를 추가하고 배포했는데, 실계정으로
다시 확인해도(같은 세션에서 2회 재질의) 여전히 0건이었다. `promising_sme`
"반려동물미용사" 항목은 같은 배포에서 정상 작동(8건)했으므로 배포 자체가
안 됐거나 캐시 문제는 아니었다 — 진짜 원인은 두 가지가 겹쳐 있었다.

## 원인 1: 띄어쓰기

로컬에서 `expand_occupation_keyword`를 직접 호출해보니, LLM이 "유치원 교사"
(사이를 띄움)로 뽑으면 표에 있는 "유치원교사"(붙여씀)와 exact-match가 전혀
안 걸렸다. 정확 일치만 하기로 한 설계(devlog 46 — 부분 문자열 포함은 다른
항목 오탐 위험 때문에 배제)의 당연한 대가지만, 흔한 띄어쓰기 변형까지는
표에 직접 반영해야 한다는 뜻이다.

## 원인 2 (더 근본적): truncation이 항상 표제어부터 살린다

`expand_occupation_keyword`는 `[조회한 키워드] + [그룹의 나머지를 원래 튜플
순서대로]`를 만들고 `limit`으로 자른다. 문제는 "그룹의 나머지"가 항상
**표제어(그룹 튜플의 0번째 원소)부터** 시작한다는 것 — 조회에 쓴 키워드가
표제어가 아닌 이상, 표제어가 항상 2번째 자리를 차지해버린다.

"유치원교사": ("유치원", "유치원 교사", "보육교사", "어린이집 교사")로
넣었을 때, training_course의 실제 캡은 `_MAX_TRAINING_KEYWORD_VARIANTS=2`다.
"유치원 교사"로 조회하면:
```
ordered = ["유치원 교사", "유치원교사", "유치원", "보육교사", "어린이집 교사"][:2]
        = ["유치원 교사", "유치원교사"]
```
그런데 "유치원교사"(표제어) **자신도 실제 과정명과 안 맞는 표현**이다 — 결국
limit=2가 전부 "안 통하는 표현 두 개"로 채워지고, 진짜 통하는 "보육교사"는
3번째 자리로 밀려 잘려나갔다. 처음 테스트를 짤 때 `limit=4`로만 검증해서
(실제 사용되는 `limit=2`가 아니라) 이 회귀를 놓쳤다.

## 수정

그룹을 하나로 묶는 대신, 관측/추정되는 표현마다 "표제어 + 보육교사" 2개짜리
독립 항목으로 쪼갰다:
```python
"유치원교사": ("보육교사",),
"유치원": ("보육교사",),
"유치원 교사": ("보육교사",),
```
이러면 `limit`이 몇이든, 어떤 표현으로 조회하든 항상 `["<조회한 표현>",
"보육교사"]`가 나와 실제로 통하는 표현이 살아남는다. 역인덱스 구성 순서상
`index["보육교사"]`는 마지막으로 처리된 항목의 그룹을 가리키게 되지만("보육교사"
자신을 조회할 때만 영향), 세 표현 각각을 조회할 때는 서로 독립적이라 문제없다.

테스트도 `limit=4`가 아니라 실제 캡인 `limit=2`로 고쳐 이 회귀를 다시 잡아낼
수 있게 했고, "유치원 교사"(띄어쓰기) 케이스도 추가했다.

## 일반화 여부에 대한 판단

같은 truncation 순서 문제가 이론상 다른 다중-동의어 항목(예: "백엔드
개발자": ("백엔드", "서버 개발"))에도 있을 수 있다 — 표제어가 아닌 동의어로
조회하면 다른 동의어가 밀려날 수 있다. 하지만 이번 라운드에서 그 항목들은
전부 표제어 자체로 조회됐을 때 문제없이 동작하는 걸 실측으로 확인했으므로,
지금 당장 전체 알고리즘을 다시 설계하지는 않는다 — 실제로 문제가 재현되는
항목이 나오면 이번처럼 "표제어+정답" 2개짜리로 쪼개는 식으로 대응한다.
