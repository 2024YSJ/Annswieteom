# 문자열 부분일치 대신 LLM이 실제로 관련 있는 결과를 고르게 하기

관련 spec: 없음(16/17과 동일하게 체크리스트 밖 항목)
날짜: 2026-09-08

---

## 배경

사용자가 "나는 백엔드 개발자야. 경기 북부에서 일자리를 구하고 싶어."라고 물었더니 직업훈련과정 카테고리가 "조건에 맞는 정보를 찾지 못했어요"만 돌려줬다. [16번 devlog](16_job_info_search_rewrite.md)에서 만든 방식은 LLM이 뽑은 검색 키워드를 워크넷 응답 텍스트에 그대로 부분일치시키는 방식이었는데, 이게 근본적으로 안 맞는 방식이었다 — "경기 북부"라는 표현이 실제 데이터엔 "의정부"/"파주"처럼 구체적인 지명으로만 나오고, "백엔드"라는 단어도 실제 과정명에는 "웹 개발"/"자바 개발자 양성"처럼 다르게 적혀 있어서 문자열이 정확히 안 맞으면 전부 걸러졌다. 사용자가 "문자열을 등록해서 인식하는 것 말고 다른 방법은 없어?"라고 정확히 짚었다.

## 완료 항목

**설계를 문자열 매칭 → LLM 판단으로 교체.**
- `classify_job_info_query`에서 카테고리별 `keywords` 추출을 없앴다(더 이상 필요 없음) — 이제 카테고리 목록만 고른다.
- 새 LLM 능력 `select_relevant_job_info_results(query, category_label, candidates)` 추가 — 워크넷에서 받아온 원본 목록(최대 20~40건)을 통째로 LLM에게 보여주고, 사용자의 **원본 질문 문장 그대로**와 비교해서 실제로 관련 있는 항목의 번호만 고르게 한다. 프롬프트에 "문자열이 정확히 안 맞아도 의미가 맞으면 관련 있다고 판단해라"는 지시와 함께, 지역/직무 판단 예시(경기 북부 ↔ 의정부/파주/고양 등, 백엔드 개발자 ↔ 웹 개발/서버 개발 등)를 명시해 실제 지리적·직무적 지식을 활용하게 했다.
- `job_info_client.py`의 `_filter_by_keywords`와 각 검색 함수의 `keywords` 파라미터를 전부 제거 — 이제 순수하게 "워크넷에서 원본을 받아오는" 역할만 한다. 관련성 판단은 전적으로 라우트(`app/api/job_search.py`)가 LLM에게 위임한다.
- 카테고리 하나당 LLM 호출이 이전엔 0개(문자열 매칭만) → 이제 1개(관련성 판단) 추가됐다. 이전에 "항목별로 LLM을 부르면 호출 수가 폭발한다"고 판단해 피했던 것(devlog 16)과 달리, 이번엔 **카테고리당 1번**(항목마다가 아니라 목록 전체를 한 번에) 호출하는 구조라 호출 수가 크게 늘지 않는다 — 관련 카테고리가 3개면 분류 1번 + 관련성 판단 3번, 총 4번.

**부수적으로 발견한 실제 버그도 고쳤다**: `search_training_courses`가 4개 엔드포인트(각 10건, 최대 40건)를 합친 뒤 `[:20]`으로 다시 잘랐는데, `asyncio.gather`가 항상 같은 순서로 도니 뒤쪽 두 엔드포인트(국가인적자원개발컨소시엄/일학습병행)의 결과가 **매번 통째로 버려지고 있었다**. 실 라이브 확인 중에 발견 — 후속 자르기를 없애고 엔드포인트별 상한(`_TRAINING_PER_ENDPOINT_LIMIT`)만으로 전체 크기를 조절하도록 고쳐서 4개 다 후보에 들어가게 했다.

## 핵심 결정 사항과 이유

**항목별이 아니라 카테고리당 한 번, 목록 전체를 한 번에 보여주는 방식을 택했다.** 개별 채용공고를 하나씩 LLM에게 판단시키던 예전 `judge_job_fit` 패턴(공백기 채우기 관련 기능에서 썼던 방식)은 항목 수만큼 호출이 늘어나 로컬 LLM 환경에서 감당하기 어렵다고 devlog 16에서 판단해 뺐었는데, 그 판단 자체는 여전히 유효하다 — 다만 "목록 전체를 한 프롬프트에 넣고 관련 있는 번호만 고르게" 하면 항목이 몇 개든 호출은 카테고리당 1번으로 고정된다. 정확도(문맥을 보고 판단)는 유지하면서 호출 수 폭발 문제는 피하는 절충점.

**관련성 판단이 실패하면(LLM 전부 불가) 그 카테고리를 아예 뺀다.** 원본 목록을 안 걸러진 채로 보여주는 건 이번에 고치려는 문제(무관한 결과 노출) 그 자체를 재현하는 것과 같아서, 차라리 그 카테고리를 숨기는 쪽을 택했다.

## 검증

- 백엔드: `select_relevant_job_info_results`가 실제로 필터링하는지(3건 중 2건만 선택), 판단 자체가 실패하면 그 카테고리를 빼는지 신규 테스트 2개 추가. 문자열 매칭 관련 테스트 2개는 그 기능 자체가 없어져서 삭제. 전체 181개 통과(순증감 0 — 늘어난 만큼 없어진 것과 상쇄).
- 실 로컬 LLM으로 사용자가 겪은 것과 동일한 질문("나는 백엔드 개발자야. 경기 북부에서...")을 직접 넣어 6개 카테고리 전부 라이브 확인 — 그 과정에서 위의 훈련과정 4-엔드포인트 절단 버그를 발견해 같이 고쳤다.
- eslint/build 클린, 프론트 e2e 8개 전부 통과(2회 연속 재현 확인) — 이번 변경은 백엔드 전용이라 프론트 코드 변경은 없음.

## 남은 작업 — 로컬 개발 환경의 알려진 한계

라이브 확인 중 로컬 LLM(`qwen2.5:3b-instruct`, 로컬 dev 전용으로 의도적으로 약한 모델 — CLAUDE.md 참고)의 관련성 판단 품질이 들쭉날쭉했다 — 일부 카테고리에서 질문과 명백히 무관해 보이는 항목을 골랐다. 이게 "LLM 기반 판단으로 바꾼 게 잘못됐다"는 뜻인지, 아니면 "로컬 dev의 약한 모델이라 그런 것"인지는 실 프로덕션 사양(RTX 4090 터널의 14b 모델 또는 Gemini)으로 같은 질문을 넣어봐야 확실히 알 수 있다 — 아직 안 함. 필요하면 프롬프트에 예시를 더 추가하거나, 모델을 바꿔가며 재확인해야 한다.
