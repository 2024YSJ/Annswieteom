# 워크넷 API 조사, 파라미터 정합성 수정, 그리고 "개인회원은 못 쓰는 API" 발견

관련 spec: 없음(11~14와 동일하게 체크리스트 밖 항목)
날짜: 2026-09-08

---

## 배경

사용자 요청: "API키에 입력으로 넣을 값을 충분히 소집하지 못했거나, 모델이 입력을 잘못 넣고 있는 것 같아. API 키의 사용법을 조사하고, 프로젝트가 재질문하거나 사용자 답변을 적절히 가공하는 기능이 부족한지 확인해줘." — 직전(14번 devlog)에 인터뷰의 재질문/가공 능력은 이미 보강했으니, 이번엔 그 결과물이 실제로 워크넷 API 호출에 얼마나 반영되고 있는지, 그리고 워크넷 API 자체의 진짜 사용법을 웹 조사로 확인해달라는 요청. 조사 도중 사용자의 인증키가 승인됐고, 사용자가 work24.go.kr의 **공식 요청 파라미터 명세서 전문**을 붙여줘서, 그걸 기준으로 코드를 다시 맞추고 실 API로 라이브 검증까지 했다.

## 1차 조사(승인 전) — 웹 자료로 확인한 것

- 워크넷(현재는 고용24로 통합, 2024-08-19) 채용정보 API는 `keyword` 외에도 `region`(근무지역), `education`(학력), `career`(경력), `minPay`/`maxPay`(급여) 등 훨씬 많은 필터 파라미터를 지원한다는 것을 공개 자료로 확인. 그런데 `worknet_client.py`는 이 중 `keyword` 하나만 실제로 보내고 있었다 — 인터뷰가 잘 수집한 `salary_min/max`, `career_years`, `education_level`은 검색 요청에 전혀 반영되지 않고 있었다. **사용자 지적("충분히 소집하지 못했다")이 정확했다.**
- 로컬 `.env`의 실 `WORKNET_API_KEY`로 라이브 호출 시 매번 `<message>유효하지 않은 인증키...</message><messageCd>002</messageCd>` 오류만 돌아왔다. work24.go.kr Open API 소개 페이지를 보니 신청 절차가 "회원가입 → 신청 → **담당자 심사** → 발급"이라 신청 즉시 발급이 아니었다(11번 devlog의 "즉시 발급" 가정은 워크넷→고용24 통합 이전 자료 기준이라 틀렸음) — 심사 대기 중이라는 가설을 세웠다.
- **더 심각했던 발견**: `worknet_client.py`가 이 오류 응답을 전혀 감지하지 못했다. HTTP 상태는 200이라 `raise_for_status()`로 안 걸리고, XML은 유효하게 파싱되지만 `<wanted>` 항목이 없어 그냥 빈 리스트를 반환 — 그 결과 사용자에게는 계속 "조건에 맞는 공고를 찾지 못했어요"라고만 떴다. **검색 결과가 항상 비어 보였던 진짜 원인이 조건 불일치가 아니라 API 실패였을 가능성이 매우 높다는 뜻.**

## 2차 조사(승인 후) — 공식 명세서 + 라이브 검증

사용자가 인증키 승인을 확인하고 work24.go.kr의 공식 요청 파라미터 명세서 전문을 제공. 이걸로 1차 조사에서 웹 검색만으로 확정 못 했던 것들을 전부 바로잡을 수 있었다:

- **요청 URL 자체가 틀려 있었다.** 계획 당시 공개 자료로 추정했던 `https://openapi.work.go.kr/opi/opi/opia/wantedApi.do`가 아니라 `https://www.work24.go.kr/cm/openApi/call/wk/callOpenApiSvcInfo210L01.do`가 맞는 엔드포인트였다.
- **`career`는 숫자가 아니라 코드였다.** 신입(N)/경력(E)/무관(Z) 중 하나를 받고, 실제 개월 수는 별도 `minCareerM`/`maxCareerM`(코드 입력 시 필수)으로 받는다 — 1차 조사에서 `career_years`를 그대로 `career`에 넣었던 건 스펙과 안 맞았다.
- **`education`은 코드였다**(00 학력무관 ~ 07 박사). 우리 쪽 값은 자유 텍스트라 매핑 함수(`_education_code`)를 새로 만들었다.
- **`minPay`/`maxPay`는 `salTp`(임금형태: D/H/M/Y) 없이 보내면 무시될 수 있다**("임금형태 입력시 필수 입력") — 값이 있으면 항상 연봉(Y) 기준으로 `salTp`를 같이 보내도록 고쳤다. 추출 프롬프트가 이미 모든 급여 표현을 "연봉 기준 만원"으로 정규화해두므로([14번 devlog](14_job_search_answer_parse_retry.md)) 실제 입력 단위와 어긋나지 않는다.

이 수정들을 실 API로 라이브 검증했더니 인증 오류는 사라졌지만(승인이 실제로 반영됨), **검색 결과가 여전히 0건**이었다. 파라미터를 하나씩 빼며 원인을 좁혀보니 `keyword`만 단독으로 보내도 0건 — 우리 쪽 파라미터 문제가 아니었다. 원본 XML을 직접 받아보니:

```xml
<GO24>
  <error>개인회원은 사용할 수 없는 OPEN-API입니다.</error>
</GO24>
```

**이 API 자체가 개인회원 계정으로는 아예 쓸 수 없는, 기업회원(사업자) 전용 API였다.** 1차 조사 때 work24.go.kr 안내 페이지에 있던 "기업회원 전용 서비스" 문구를 봤었는데, 그때는 "가입 시 회원 유형을 고르는 절차겠거니" 정도로 넘겼던 게 실제로는 진짜 하드 블로커였다.

이 오류 형태(`<GO24><error>`)도 기존 `<wantedRoot><message>` 감지 로직으로는 못 잡는 **완전히 다른 XML 구조**라, 이것도 조용히 "결과 없음"으로 보였을 것 — 감지 로직에 이 형태도 추가했다.

## 완료 항목

- **`WorknetApiError`가 관찰된 오류 응답 두 형태를 모두 감지**: `<wantedRoot><message>/<messageCd>`(인증키 오류)와 `<GO24><error>`(권한 오류, 예: 개인회원 차단). `search_jobs` 라우트가 이를 잡아 503 + `detail="worknet_unavailable"`로 변환, 프론트에 "채용정보를 가져오지 못했습니다. 잠시 후 다시 시도해주세요" 매핑, "결과 없음" 문구와 겹쳐 뜨지 않도록 `JobSearchResultsSection.tsx` 정리.
- **요청 파라미터를 공식 명세서에 맞춰 재작성**: base URL 교체(`config.py`), `salTp`+`minPay`/`maxPay`, `career`(N/E/Z)+`minCareerM`/`maxCareerM`, `education`(00~07 코드, `_education_code` 자유 텍스트 매핑 함수) 전부 실제 API 파라미터로 반영. 지역은 여전히 코드 매핑 없이 `keyword`에 자유 텍스트로 섞는다(아래 참고).
- 백엔드 신규/수정 테스트로 전체 195개 통과, eslint/build 클린. 실 인증키로 여러 차례 라이브 검증(파라미터를 하나씩 빼며 원인 격리, 새 오류 감지 로직이 실제로 발동하는지 확인) — 비밀 값은 한 번도 출력하지 않음.

## 핵심 결정 사항과 이유

**지역 코드 매핑은 여전히 손대지 않았다.** 이번 공식 명세서에도 "근무지역코드 보기"라는 링크만 있고 실제 코드표는 별도 페이지라 이번엔 확보 못 했다. 학력/경력처럼 코드가 소수(6~8개)로 고정된 게 아니라 지역은 훨씬 세분화돼 있어서 잘못 매핑하면 검색이 조용히 좁아질 위험이 더 크다고 판단, 기존처럼 자유 텍스트를 `keyword`에 실어 보내는 방식을 유지했다.

**대졸(2~3년제 vs 4년제) 구분은 "대졸"만 언급되면 4년제(05)로 기본 처리한다.** 사용자가 "전문학사"/"2년제" 같은 명시적 단서를 안 주면 일상 표현에서 "대졸"이 가리키는 가장 흔한 뜻(4년제)을 기본값으로 삼았다 — 잘못 짐작할 여지는 있지만, 아예 필터를 안 거는 것보다는 실용적이라 판단.

## 남은 작업 (우선순위 순)

1. **이 기능 자체가 지금 상태로는 못 쓴다(사용자 결정 필요).** 워크넷 채용정보 API가 개인회원 계정을 거부하므로, 다음 중 하나를 택해야 실제로 동작한다: (a) 사업자등록번호로 기업회원 전환/가입(학생 프로젝트에선 현실적으로 어려울 수 있음), (b) 사람인/잡코리아 등 개인도 쓸 수 있는 다른 구인 API로 교체, (c) 이 기능 자체를 데모/제출 범위에서 보류. 코드는 API가 정상 열리면 바로 쓸 수 있는 상태로 맞춰뒀지만, 지금은 실제 검색이 항상 실패한다.
2. (a)를 택해 진짜로 열리면: `minPay`/`maxPay`/`career`/`minCareerM`/`maxCareerM`/`education`이 실제로 필터링에 반영되는지, `_parse_postings`가 가정한 응답 태그명이 명세서와 일치하는지(공식 명세서 기준으로는 맞게 고쳤지만 실 성공 응답으로 아직 확인 못 함) 한 번 더 확인.
3. 지역 코드 매핑표 확보 — (a)로 진행하게 되면 work24.go.kr 회원 페이지에서 "근무지역코드 보기" 링크를 직접 열어 확인 가능할 것으로 보인다.
