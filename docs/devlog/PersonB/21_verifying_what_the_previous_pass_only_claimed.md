# 앞 작업이 "확인 안 함"으로 남겨둔 것들을 실제로 확인하기

관련 spec: 없음([20번](20_differentiation_from_a_chat_window.md)의 "남은 작업" 소진)
날짜: 2026-09-09

---

## 배경

20번에서 벡터 검색·활동 기간 유추·커버리지를 붙였지만 남은 작업에 이렇게 적었다: "벡터 검색을 실 데이터로 확인하지 않았다", "`extract_activity_period`의 실 LLM 품질 미확인", "커버리지 UI 미구현", "`GET /me/answers`를 쓰는 화면이 없다". 이번엔 그걸 전부 확인하고 채웠다. 확인해보니 **두 개 중 하나는 잘 돌아갔고, 하나는 그대로 뒀으면 기능 전체를 조용히 무의미하게 만들 상태였다.**

작업 시작 시점에 작업 트리에는 [Gemini 제거 리팩터링](../../../CLAUDE.md)이 이미 얹혀 있었다(`FallbackProvider`/`FallbackEmbedding` 삭제, `AllProvidersFailedError` → `LLMUnavailableError`, `get_llm_provider`가 패키지 `__init__`으로 이동). 20번의 코드는 그 리팩터링에 맞춰 이미 조정돼 있었고, 전체 테스트 232개가 통과하는 것을 먼저 확인한 뒤 시작했다.

## 완료 항목

### 1. 벡터 검색 — 실 pgvector + 실 bge-m3로 확인 (통과)

dev Supabase에 임시 세션을 만들고, 서로 다른 내용의 청크 5개를 실제 bge-m3로 임베딩해 넣은 뒤 조회했다. **"힘들었던 점과 해결"에 해당하는 청크를 일부러 목록 맨 뒤(작성순 5번째)에 뒀다** — 예전 동작(`created_at LIMIT`)에서는 구조적으로 top-2에 올라올 수 없는 자리다.

```
pgvector extension: 0.8.2
embedded 5 chunks, dim=1024, model=bge-m3
question: 진행하면서 힘들었던 점은 무엇이었고, 어떻게 해결하셨나요?

-- vector search (top 2) --   [4] 프로젝트에서 가장 힘들었던 점은 배포 파이프라인이...
-- recency (old behaviour) -- [1] 주말에 친구들과 한강에 다녀왔다...

VECTOR  ranks the matching chunk first: True
RECENCY surfaces it at all in top 2   : False
```

20번에서 주장만 했던 것이 실제로 그렇게 동작한다. 차원(1024)도 `EMBEDDING_DIM`과 일치한다. 확인 후 임시 데이터는 삭제했다.

### 2. 활동 기간 유추 — 실 LLM로 확인 (실패 → 판단을 코드로 옮김)

`qwen2.5:3b-instruct`로 5개 케이스를 3회씩 돌렸더니 **가장 위험한 실패가 나왔다: 단서가 전혀 없는 사실을 주면 "모르겠다" 대신 공백 기간 전체를 그대로 베껴 돌려줬다(3/3).** 프롬프트에 "공백 기간 전체를 그대로 베껴 쓰지 마라"고 명시해도 그랬다. 그 답을 저장하면 커버리지가 100%가 되고, 빈 구간이 하나도 안 남고, 커버리지 기능 전체가 조용히 무의미해진다 — 티도 안 나게.

프롬프트를 세 가지 형태로 A/B해본 결과가 더 결정적이었다:

| 변형 | 명시적 날짜 | 단서 없음 |
|---|---|---|
| 예시 4개 + null 분기 마지막 | 0/3 | null (정답) |
| 예시 4개 + 긍정 분기 마지막 | 3/3 | 공백기 전체 (오답) |
| 예시 2개 + 긍정 분기 마지막 + `활동 카테고리` 줄 제거 | 3/3 | null (정답) |

개별 변경은 아무 효과가 없고 **조합에서만** 동작했다(예시 축소만 0/3, 카테고리 줄 제거만 0/3, 둘 다 3/3). 즉 이 모델에서는 입력 내용이 아니라 프롬프트 표면이 결과를 좌우한다. 프롬프트만으로는 신뢰할 수 없다고 판단하고, **모델에게는 추출만 시키고 "모른다"는 판단은 코드로 가져왔다**:

- `coverage.has_period_clue()` — 확정 사실에 숫자+기간 단위(`2025년`, `6개월`, `3주`) 또는 상대 표현(`작년`, `지난달`, `하반기`)이 하나도 없으면 **LLM을 아예 호출하지 않는다.** "주 3회"(빈도), "저녁 6시부터"(시각), "매일 4시간씩"(하루 분량)은 활동이 언제/얼마나 이어졌는지를 말해주지 않으므로 단서로 치지 않는다. LLM 호출도 한 번 아낀다.
- `clamp_activity_period()` — 결과가 **공백 기간과 정확히 같으면 버린다.** 이건 관찰이 아니라 모델이 입력을 되뱉은 것이다.

프롬프트도 위 표의 3번 형태로 고정하고, 그 형태가 실측으로 고른 것이며 예시/필드를 늘리면 다시 재봐야 한다는 것을 템플릿 상단 주석에 남겼다.

최종 실측 결과 — **위험한 과대 보고는 전 케이스 0건**:

| 케이스 | 결과 |
|---|---|
| 명시적 시점 ("2025년 3월부터 8월까지") | 2025-03-01 ~ 2025-08-31 (3/3) |
| 길이만 ("6개월 동안") | None (과소 보고) |
| 단서 없음 ×2 | None (정답) |
| 공백기 밖 연도 (2020년) | None (정답) |

### 3~4. 커버리지 UI + 문답 아카이브 화면

- `components/CoverageSection.tsx` — 채움 비율 막대, 빈 구간 목록, 구간별 "이 시기 이야기하기" 버튼(`POST /coverage/fill` → 세션 컨텍스트 무효화로 인터뷰가 새 카테고리로 이동). `INTERVIEWING`/결과 화면 양쪽에서 보인다 — 문서를 만들기 전에 마지막으로 빈 시기를 확인할 수 있도록. 기간 미상 카테고리가 있으면 "실제로는 더 채워져 있을 수 있다"고 명시한다(비율이 하한선이라는 사실을 숨기지 않는다).
- `app/archive/page.tsx` + 헤더 링크 — 계정에 쌓인 문답을 질문/답변 원문/확정된 사실과 함께 보여주고 개별 삭제까지. 원문이 계정에 계속 남는 이상 지울 방법도 같이 있어야 한다. 게스트에게는 링크를 숨기고(눌러도 안내뿐), 비회원 상태에서는 "가입하면 비회원으로 남긴 답변도 이어진다"고 알려준다.
- `lib/api/coverage.ts`, `lib/api/profile.ts`, 쿼리 키 2개 추가.

## 핵심 결정 사항과 이유

**과소 보고를 택했다.** `clamp_activity_period`의 "공백기 전체와 같으면 버린다" 규칙은 실제로 공백기 내내 이어진 활동을 억울하게 버린다. 그래도 이쪽을 택한 이유는 두 오류의 대가가 다르기 때문이다 — 과소 보고는 이미 설명한 구간에 대해 질문을 한 번 더 받는 것으로 끝나지만, 과대 보고는 빈 구간을 통째로 숨겨 기능을 무의미하게 만든다. 사용자는 `PATCH .../period`로 직접 정정할 수 있다.

**"모른다"를 모델에게 맡기지 않는다.** 3b 모델은 추출은 하지만 기권을 못 한다. 기권 판단을 정규식 게이트와 결정론적 후처리로 옮기면, 모델 품질이 바뀌어도 안전 방향은 유지된다.

## 트러블슈팅

**케이스 1(명시적 날짜)이 계속 null이라 프롬프트 버그를 의심했다.** 렌더된 프롬프트를 통째로 찍어보고서야 템플릿·변수·사실 목록이 전부 정상이라는 걸 확인했다 — 모델이 그냥 null을 뱉고 있었다. 원본 응답(`_generate` 반환값)을 직접 찍는 게 결국 가장 빨랐다.

**게이트를 추가하니 기존 테스트 1개가 깨졌다.** `test_activity_period_is_inferred_...`가 `"답변입니다"`라는 기본 답변을 쓰고 있었는데, 여기엔 기간 단서가 없어 게이트가 먼저 막았다. 답변을 `"3개월 동안 주 3회 일했어요"`로 바꿔 게이트를 통과시켰다 — 테스트가 검증하려는 건 게이트 뒤의 유추 동작이므로.

## 검증

- 백엔드 pytest **232 → 243개 통과**. 신규 11개: `has_period_clue` 6개(빈도/시각/하루 분량이 단서로 오인되지 않는지 포함), `clamp_activity_period` 5개(공백기와 정확히 같으면 버리고, 하루 짧으면 남기는지).
- **실 uvicorn + 실 Supabase 스모크 15/15 통과** — pytest가 SQLite+가짜 LLM이라 못 보는 것들: 라우트 순서(`/records/uncited`가 `/{record_id}`에 안 먹히는지), 실 Postgres의 `period_source` CHECK 제약, `coverage/fill` 왕복, 게스트 403, 인터뷰 중 기록물 첨부 201. 만든 계정·게스트 행은 확인 후 삭제했다.
- 프론트: `tsc --noEmit` / `eslint` / `next build --webpack` 클린, `/archive` 라우트 생성 확인.

## 남은 작업

- **브라우저에서 커버리지/아카이브 화면을 직접 보지 않았다.** 타입·빌드·API 왕복은 확인했지만 실제 렌더링과 상호작용(빈 구간 버튼을 눌렀을 때 인터뷰가 그 카테고리로 넘어가는 흐름)은 미확인이다. e2e 스펙도 아직 안 붙였다.
- **`extract_activity_period`를 프로덕션 모델로 재확인해야 한다.** 지금 프롬프트 형태는 3b의 표면 민감도에 맞춰 고른 것이라, 14b에서는 예시를 늘리는 편이 더 나을 수 있다. 다만 RTX 4090 서버/터널이 아직 준비되지 않았고 Gemini도 제거돼서, 지금 이 랩탑에서 더 큰 모델로 재볼 방법이 없다.
- "길이만 있고 시점이 없는" 케이스(예: "6개월 동안")는 현재 None으로 떨어진다. 안전한 방향이긴 하지만 recall 손실이다 — 필요하면 이것도 코드로(공백기 시작 + 길이) 계산할 수 있다.
- `/me/answers`를 **인터뷰 중에** 활용하는 부분("예전에 비슷한 질문에 이렇게 답하셨어요")은 여전히 없다. 지금은 열람·삭제 전용 화면이다.
- `MIN_REPORTABLE_GAP_DAYS`(30일), `LONG_ACTIVITY_DAYS`(180일), `consistency_threshold`(0.55)는 여전히 실제 샘플로 조정하지 않은 값이다.
