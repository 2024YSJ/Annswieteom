## 배경

취업 정보가 `job_search` 세션 안에서 **사용자가 먼저 질문해야만** 나왔다. 뭘 물어야 할지 모르는 사용자에게는 아무것도 안 보인다. 사용자 요청: "메인 화면에서 사용자 맞춤 취업처/지원 정책들을 게시판 뉴스처럼."

만든 것 세 가지: 청년 지원 정책(최신 등록순), 공고(최신순), 맞춤 공고(개인화).

## 완료 항목

- **테이블 4개** — `feed_items`(전 사용자 공용 캐시), `feed_item_embeddings`, `user_profile_embeddings`, `feed_refresh_states`. 마이그레이션 `e7a1c93d5b20`, downgrade 왕복까지 실 DB에서 확인.
- **소스 레이어** `app/services/feed/sources/` — 워크넷 어댑터는 기존 `CATEGORY_SEARCH_FUNCTIONS`를 호출만 하고 HTTP 코드가 한 줄도 없다. 온통청년은 신규(미검증, 아래).
- **수집** `ingest.py` — CAS 락, 포터블 upsert, 임베딩 backfill, 14일 정리.
- **개인화** `profile_adapter.py` + `ranking.py` — `interview_answers` 자유 텍스트 → bge-m3 → pgvector 코사인.
- **엔드포인트 3개** `GET /feed/{policies,jobs,jobs/recommended}`.
- 테스트 신규 45개(API 19 / 수집·dedup 12 / 프로필 어댑터 10 / 온통청년 4+xfail 1), 전체 **288 passed**.
- **실 데이터 검증**: 워크넷 6개 카테고리에서 137건 수집, 137건 전량 임베딩, 실패 소스 0. 정책 피드 59건.

## 핵심 결정 사항과 이유

**벡터를 본체가 아니라 1:1 곁테이블에 뒀다.** pgvector의 `Vector`는 SQLite 컴파일러가 없어서, `feed_items`에 벡터를 얹으면 `conftest.py`가 그 테이블을 만들 수 없고 피드 API 전체가 API 레이어에서 테스트 불가능해진다(`record_chunks`가 대부분의 픽스처에서 빠져 있는 것과 같은 이유). 대가는 조인 하나와 — 정직하게 적자면 — **실제 코사인 정렬이 CI 미검증으로 남는다는 것**이다. SQLite로는 검증할 방법이 없고 Postgres 테스트 컨테이너는 이번 범위 밖이라, 아래 수동 검증으로만 확인했다.

**훈련과정·구직자취업역량강화프로그램을 `policy`로 분류했다.** 온통청년 인증키는 워크넷과 같은 담당자 심사를 거치는데 아직 안 나왔다. 이 두 줄 덕에 키가 영영 안 나와도 지원 정책 섹션이 비지 않는다(실측 59건). 억지 분류도 아니다 — 둘 다 실제로 정부 지원 프로그램이다.

**개인화 입력이 구조화 필드가 아니라 자유 텍스트인 게 오히려 낫다.** 옛 `job_search_preferences`(희망지역/학력/경력연차)가 있었다면 "경기 북부"를 "의정부/파주"에 매핑하는 표를 손으로 만들어야 했다 — devlog 18에서 문자열 매칭을 폐기한 바로 그 이유다. bge-m3에 사용자가 쓴 문장을 그대로 넣으면 매핑 표도 LLM 호출도 없이 의미로 붙는다. **이 기능은 LLM을 한 번도 호출하지 않는다** — 로컬 모델이 3b든 72b든 피드 품질과 무관하다.

**`question_text`는 프로필 텍스트에서 뺐다.** 질문 은행이 만든 시스템 문구라 사용자 간에 거의 동일하다. 넣으면 모든 프로필 벡터에 큰 공통 성분이 생겨 사용자 사이 코사인 거리가 압착되고 개인화가 노이즈로 뭉개진다.

**미확정 답변도 프로필에 넣는다.** 리뷰에서 반드시 나올 지점이라 근거를 남긴다: 정직성 가드레일은 "생성 문서가 무엇을 인용할 수 있는가"를 규율한다(`document_generator`는 여전히 `confirmed_facts`만 받고, `interview_answers`는 생성 입력에서 제외돼 있다 — devlog 22). 피드는 문장을 만들지도 인용하지도 않고 공개 공고의 순서만 바꾼다.

**`interview_answers`를 읽는 지점을 파일 하나로 가뒀다.** 그 테이블은 다른 작업의 소유고 아직 커밋도 안 됐다. `profile_adapter.py` 상단에 의존하는 컬럼 5개를 명시하고, 테이블이 없거나 바뀌면 예외 대신 빈 신호를 돌려준다 — 다른 팀의 스키마 변경이 메인 화면을 500으로 만들면 안 된다. `GET /me/answers`를 HTTP로 부르지 않은 이유도 적어뒀다(게스트 403 + 화면용 필터라 랭킹 입력과 계약이 다르다).

**`feed_kind`를 파생값이 아니라 컬럼으로 뒀다.** 코사인 정렬만 하면 한 카테고리가 화면을 다 먹는 문제가 있는데, 프론트가 두 섹션을 각각 조회하게 하면 별도 다양성 로직 없이 해결된다.

## 트러블슈팅

| 증상 | 원인 | 해결 |
|---|---|---|
| `/feed/jobs/recommended`가 `MissingGreenlet`으로 500 | 프로필 조회 실패 시 부르는 `db.rollback()`이 세션의 ORM 객체를 전부 expire시킨다 — 그 뒤 `current_user.id`를 읽자 lazy refresh(IO)가 일어났고 요청 핸들러에는 greenlet 컨텍스트가 없다 | 라우트 진입 직후 `user_id`를 지역 변수로 붙잡아 둔다. 테스트에서 먼저 잡혔지만 프로덕션에서도 차원 불일치 등으로 같은 경로를 탄다 |
| 갱신 락 UPDATE가 `can't compare offset-naive and offset-aware datetimes` | ORM `update()`가 기본적으로 WHERE 절을 파이썬에서 재평가해 세션 객체와 맞춰본다. SQLite가 돌려준 naive datetime과 aware 바인드 값이 거기서 부딪혔다 | CAS는 DB에서만 판정되면 되고 결과는 `rowcount`로 읽으므로 `.execution_options(synchronize_session=False)` |
| 벡터 테이블이 없는 환경에서 임베딩 단계 예외가 세션을 오염시켜 이후 단계까지 죽음 | `_embed_pending`의 첫 쿼리가 try 밖에 있었고, 뒷단 두 단계를 하나의 try로 묶어놨다 | 쿼리를 try로 감싸고, 단계별로 독립 try + rollback. 임베딩이 안 됐다고 오래된 항목 정리까지 건너뛸 이유가 없다 |
| **정상 사용자에게 "AI 서버가 수리 중이예요"가 떴다** | 문답을 처음 남긴 사용자는 "기록은 있는데 벡터는 아직 없음"을 **반드시 한 번** 지나가는데, 그 상태를 고장과 같은 `ai_unavailable`로 묶어놨다 | `preparing`을 세 번째 상태로 분리. 라이브 검증에서만 잡힌 문제다 — 단위 테스트는 내가 쓴 잘못된 기대를 그대로 통과시키고 있었다 |

## 실 데이터 검증

정반대 아카이브를 가진 계정 둘을 만들어 같은 엔드포인트를 호출했다. 이게 개인화가 실제로 걸렸다는 유일한 증거다(위에 적은 대로 CI는 이걸 못 덮는다).

- **반도체 프로필** → `[경력] 반도체 CLN 설비 공정 담당자 모집(안성)`, `[경력] 반도체 CMP 장비 정밀설계 담당자 모집(동탄)`
- **사회복지 프로필** → `(주)코리아메디케어`, `(주)서흥헬스케어 구인구직 만남의 날`

상태 전이도 실제로 확인: 벡터 없음 → `preparing` → (백그라운드 임베딩) → `personalized: true`.

## 남은 작업

- **`JobInfoResult.source_key`** — 워크넷 응답에 `eventNo`/`empSeqno`가 실제로 있는데 `JobInfoResult`가 안 들고 있어서 못 쓴다. 지금은 상세 URL이 있으면 그걸, 없으면 내용 해시로 대체한다. `job_info_client.py`를 크게 고치는 작업(`worktree-sidebar-wrap-and-llm-harness`)과 겹쳐서 병합 후로 미뤘다. **후속 1순위** — 그쪽의 `(title, subtitle)` dedupe도 `source_key` 우선으로 바꾸기로 합의했다.
- **온통청년 실연동** — 인증키 신청이 먼저다. 파서는 후보 태그를 여러 개 시도하는 형태로 써뒀고 테스트는 `xfail`이다. 키가 나오면 `curl` → 실 응답을 테스트 상수로 → 후보를 정답 하나로 줄이는 순서.
- **프론트 연동 전체.** ⚠️ `app/page.tsx`가 세션이 1개 이상인 로그인 사용자를 곧바로 최근 세션으로 리다이렉트한다 — **프로필이 쌓인 바로 그 사용자가 랜딩을 못 본다.** 피드를 어디에 그릴지부터 정해야 기능이 보인다.
- ivfflat 인덱스는 안 만들었다. 수백 행에서는 seq scan이 더 빠르고(`lists`를 정하려면 데이터가 먼저 있어야 한다), 필요해지면 init 마이그레이션과 같은 raw SQL로 추가하면 된다.
