# 50. 여러 주제가 섞인 대화 이력에서 후속 좁히기 질문이 실패하는 버그 (2026-09-15)

27개 직업 실계정 테스트 라운드에서 재현 가능한 버그를 발견했다. 세션 하나에서
서로 무관한 직무를 5턴 연속 물은 뒤(상담심리사→승강기정비사→게임기획자→
배달라이더→**전기기사**), "그중에서 서울 지역만 보여줘"라고 물으면 **0건**이
나왔다.

## 재현·대조 확인

- 직전에 "전기기사"만으로 물었을 때는 서울 항목 2개 포함 8건 정상.
- "그중에서 서울만" 대신 "서울 전기기사 훈련과정 있어?"라고 대놓고 다시
  물으면(같은 오염된 히스토리가 남은 채로) 8건 정상.
- 무관한 다른 주제 없이 "전기기사 관련 채용훈련과정 알려줘" → "그중에서 서울
  지역만 보여줘" 두 턴만으로 새 세션에서 반복하면 정상(대조군).

즉 "직무를 다시 말하지 않는 후속 질문" 처리(devlog 45) 자체는 살아있지만, 그
직전에 서로 다른 주제가 여러 번 섞여 있으면 깨진다.

## 원인

`history`(최근 5턴 사용자 발화 원문, 오래된 것부터)는 `classify_job_info_query`,
`extract_job_info_query_params`, `select_relevant_job_info_results` 세 LLM 호출
모두에 완전히 동일하게, 가공 없이 전달된다(`job_search.py:176`). 세 프롬프트
파일을 원문으로 확인한 결과, **"이전 대화에 여러 주제가 섞여 있으면 가장 최근
것만 유효하다"는 규칙이 어디에도 없었다** — 세 파일 모두 "이전 대화" few-shot
예시가 전부 한 턴짜리, 같은 주제뿐이었다. 실패 세션 히스토리엔 지역 언급이
전혀 없었으므로(직무만 5개 연속), 직무 키워드 쪽 다중 주제 처리 공백이 가장
유력한 원인으로 판단했다.

devlog 44는 애초에 "history를 원문 그대로 넘기는 방식이 맞는지 나중에
재검토"라는 TODO를 남겨둔 채 devlog 45(단일 주제 버그)만 고치고 멈춰 있었다 —
이번이 그 TODO가 실제로 문제가 된 첫 사례다.

## 프롬프트 엔지니어링으로 해결 가능한가

가능하다고 판단했다. 모델(프로덕션 qwen3.5:35b-a3b)은 히스토리 전체를 이미
받고 있고 "가장 마지막 턴이 최신"이라는 정보도 리스트 순서로는 들어있다 —
다만 여러 주제가 섞였을 때 어떻게 우선순위를 매길지 명시적으로 알려준 적이
없었다. 모델 능력의 한계라기보다 지시 공백에 가깝고, devlog 45에서 비슷한
성격의 공백을 few-shot 하나로 메운 전례가 있어 같은 방식을 적용했다.

## 수정

세 프롬프트 파일 모두에 "[이전 대화]에 서로 다른 직무/주제가 여러 번
등장하면 **가장 최근(마지막) 턴**만 유효하다 — 더 이전 것은 지나간 주제이니
무시해라"는 규칙과, 정확히 이 버그(승강기정비사→게임기획자→배달라이더→
전기기사 → "그중에서 서울만")를 재현하는 few-shot 예시를 추가했다:

- `extract_job_info_query_params.jinja`: 직무/분야 규칙 블록에 추가 +
  `{"regions": ["서울"], "keywords": ["전기기사"]}` 예시.
- `select_relevant_job_info_results.jinja`: 기존 "[이전 대화]가 있으면 반드시
  참고해라" 블록 뒤에 추가 + 후보 목록(서울·전기기사 포함, 서울·무관직무 제외,
  타지역·전기기사 제외)과 함께 재현하는 예시. **새 예시는 기존 마지막 예시
  (exhaustive selection 회귀 테스트가 고정한 자리) 바로 앞에 삽입** —
  devlog 45에서 겪은 실수(새 예시를 마지막 뒤에 붙였다가 회귀 테스트가 잡아냄)를
  반복하지 않았다.
- `classify_job_info_query.jinja`: 이번 버그에서 카테고리 선택 자체는
  정상이었지만, 세 프롬프트의 일관성을 위해 같은 규칙과 예시를 방어적으로
  추가했다.

## eval_job_search.py 골든셋 추가 (실행은 보류)

지난 라운드와 같은 이유로 실제 프로덕션 터널 실행은 이번에도 요구하지
않았다 — 나중에 실행할 때 이 버그가 다시 잡히도록 골든셋에만 추가했다.

- `Case`에 `expected_keywords_any_of` 필드와 `_score_keywords` 채점 함수를
  추가(정확한 표현을 강제하지 않고 "이 중 하나라도 있으면 통과"로 느슨하게
  채점 — 규칙상 실제 데이터 표현으로 바꿔 적으라고 하므로 "전기기사" 대신
  "전기"가 나와도 맞을 수 있다).
- `CASES`에 `multi_topic_history_keeps_only_last_job` 케이스 추가(5턴 히스토리
  그대로 재현).
- `RELEVANCE_CASES`에 같은 이름의 케이스 추가(합성 후보 3개로
  `select_relevant_job_info_results`가 서울·전기기사 항목만 고르는지 채점).

## 검증 (배포 후 진행)

정확히 실패했던 시퀀스를 브라우저로 재현: 새 세션에서 "상담심리사 관련
훈련과정 있어?" → "승강기정비사 관련 훈련과정 있어?" → "게임기획자 관련
훈련과정이나 채용공고 있어?" → "배달라이더 구인 정보 있어?" → "전기기사 관련
채용훈련과정 알려줘" → "그중에서 서울 지역만 보여줘" — 마지막 턴이 실제로
서울 전기기사 항목을 반환하는지 확인.
