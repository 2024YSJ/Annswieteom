# 27~28단계 — 배포는 됐는데 DB는 그대로였던 날, 그리고 다시는 안 물어보던 질문

[05_local_dev_split_and_the_interview_loop_bugs.md](05_local_dev_split_and_the_interview_loop_bugs.md)에서 다룬 변경을 `main`에 머지하고 배포한 직후, 실제 프로덕션에서 "게스트로 접속했는데 오류가 나서 접속이 안 된다"는 신고와 "인터뷰가 진행되다가 멈춘다"는 신고가 연달아 들어왔다. 둘 다 코드 리뷰만으로는 못 잡는, 실제로 재현해봐야만 보이는 종류의 문제였다.

## 27단계 — 코드는 배포됐는데 컬럼은 없다

첫 신고("게스트 접속이 안 됨")를 프로덕션 API에 직접 요청을 보내 재현해보니, 게스트 로그인과 세션 생성은 멀쩡한데 **카테고리 선택 단계에서 500 에러**가 났다. 원인은 명확했다 — 어제 머지한 변경에 `activity_categories.questions_asked` 컬럼을 추가하는 마이그레이션이 포함돼 있었는데, Render는 새 코드를 배포했지만 그 마이그레이션은 프로덕션 Supabase DB에 실행된 적이 없었다. 코드는 이미 이 컬럼이 있다고 가정하고 INSERT하는데, 실제 테이블에는 없으니 그 즉시 500.

여기서 한 가지 확인 과정이 꼬였다 — 마이그레이션을 어디서 적용해야 하는지(로컬 개발 컴인지 "서버컴"인지), DATABASE_URL을 어디서 찾아야 하는지(Render Environment 탭이 아니라 Supabase 대시보드였다) 순서로 오해가 있었다. 결국 가장 확실한 방법으로 풀었다 — Supabase SQL Editor에 마이그레이션과 정확히 같은 내용의 `ALTER TABLE` 두 줄을 직접 실행했고, `information_schema.columns`로 컬럼이 실제로 생겼는지 확인한 뒤에야 API를 다시 재현해서 카테고리 선택부터 인터뷰 첫 질문까지 정상 작동하는 걸 확인했다.

## 28단계 — 확인은 됐는데, 다음 질문이 안 온다

두 번째 신고는 스크린샷과 함께 왔다 — "공모전" 카테고리에서 첫 질문에 답하고 "확인됨" 표시까지 떴는데, 그 뒤로 아무 것도 안 뜨고 입력창만 덩그러니 남아있는 화면이었다. 프로덕션 API에 똑같은 흐름(같은 카테고리, 같은 답변)을 직접 재현해봤는데 — 이상하게도 API 자체는 4~7초 안에 전부 정상 응답했다. `interview/confirm`도, 그 다음 파고들기 질문 생성도 전부 빠르고 문제없이 끝났다. 백엔드는 결백했다.

그렇다면 남은 건 프론트엔드였다. `InterviewSection.tsx`를 다시 읽어보니 진짜 원인이 보였다 — 다음 질문을 불러오는 코드가 `useEffect`로 짜여 있었는데, 이 effect는 `status`나 `currentCategoryId`가 "바뀔 때"만 다시 실행된다. 그런데 같은 카테고리 안에서 다음 질문으로 넘어가는 경우(남은 고정 질문이든, AI가 중간에 끼워넣는 파고들기 질문이든) 이 두 값은 전혀 바뀌지 않는다. 답변을 확인하는 `submit()` 함수는 "이 effect가 알아서 다시 돌겠지"라고 가정하고 `fetchedForRef.current = null`만 해뒀는데, ref를 리셋하는 것만으로는 React가 effect를 다시 실행해주지 않는다 — 의존성 배열의 값이 실제로 바뀌어야 한다. 결과적으로 확인은 되지만 다음 질문을 불러오는 코드 자체가 다시는 실행되지 않았다.

돌아보면 이건 오늘 만든 "AI 파고들기" 기능 때문에 생긴 버그가 아니라, 인터뷰 엔진을 처음 만들 때부터 있던 버그였다. 다만 예전에는 한 카테고리 안에서 여러 질문을 실제 브라우저로 연속해서 클릭해본 사람이 없었을 뿐이고, 파고들기 기능이 "같은 카테고리에 머무는" 상황을 훨씬 자주 만들면서 마침내 드러난 것 같다.

고친 방식: `submit()`이 confirm 성공 직후 프롭이 바뀌기를 기다리지 않고, 직접 다음 질문을 요청하도록 바꿨다. 카테고리가 바뀌는 경우와 안 바뀌는 경우 둘 다 한 함수 안에서 명시적으로 처리하고, `fetchedForRef`를 미리 채워둬서 혹시 나중에 effect가 실행되더라도 중복 요청이 안 나가게 했다.

이번엔 API만으로는 검증이 안 되는 문제라(버그 자체가 브라우저의 React 렌더링 흐름 안에 있었으므로), 로컬 개발 서버에 대해 실제 Playwright로 브라우저를 띄워 정확히 같은 시나리오(같은 카테고리에서 두 번째 질문까지)를 재현했다. 처음 두 번은 테스트 스크립트 자체의 타이밍 문제(질문이 로드되기 전에 답을 입력해버림, 느슨한 텍스트 매칭으로 오탐)로 잘못된 결론을 낼 뻔했는데, 네트워크 요청 로그를 직접 찍어보고 나서야 확실히 잡을 수 있었다 — `confirm` 다음에 새 `ask` 요청이 실제로 나가는지, 그리고 "확인됨"이라는 명확한 텍스트가 뜨는지를 기준으로 삼으니 화면 스크린샷으로도 고쳐졌다는 걸 눈으로 확인할 수 있었다.
