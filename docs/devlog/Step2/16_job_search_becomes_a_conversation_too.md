# 일자리 찾기도 대화가 되다

[15장](15_job_search_and_the_two_paths_home.md)에서 일자리 찾기를 만들 때, 조건 입력은 "어떤 조건의 일자리를 찾고 계신가요? 급여, 근무지, 학력·경력, 업무 스타일을 자유롭게 말씀해주세요"라는 열린 질문 하나였다. 그 직후 요청으로 확정된 조건을 나중에 다시 대화로 고칠 수 있게는 만들었지만, 정작 **처음 입력**은 여전히 빈 화면에 다 적어 넣는 방식 그대로였다. 사용자가 "공백기 채우기처럼 하나씩 물어보면 더 자연스러울 것 같다"고 요청했다 — 실제로 공백기 채우기는 카테고리마다 질문을 하나씩 던지고 AI가 초안을 제안하면 확인만 하면 되는데, 일자리 찾기의 첫 입력만 유독 다른 방식이었던 셈이다.

## 숨어 있던 빈틈

턴 기반으로 바꾸려고 기존 코드를 다시 들여다보다가, 설계와 무관한 진짜 빈틈을 하나 발견했다. 워크넷 검색에 실제로 넘어가는 키워드가 희망 근무지·학력·업무 스타일 태그를 억지로 이어붙인 문자열뿐이었다 — 정작 사용자가 "어떤 일을 찾고 있는지"(직무·분야) 자체는 스키마에 없었다. 검색 품질을 생각하면 이게 제일 중요한 값인데 빠져 있었던 것이다. 이번 참에 `desired_keyword`라는 새 필드를 추가해서 첫 질문으로 넣기로 했다.

## 6개의 질문, 하나씩

새로 만든 대화는 고정된 6개 질문 — 직무/분야, 근무지, 급여, 학력, 경력, 업무 스타일 — 을 순서대로 하나씩 던진다. 사용자가 답하면 AI가 자유 텍스트에서 값을 뽑아 후보로 보여주고, 사용자가 확인하거나 고쳐서 "다음"을 누르면 다음 질문으로 넘어간다. 6개를 다 답하면 그제야 익숙한 "확인됨" 요약 화면(과 그 뒤의 자유 재편집 기능)으로 넘어간다. 공백기 채우기 인터뷰와 원리는 완전히 같지만, 필드마다 값의 생김새가 다르다(문자열 하나, 숫자 하나, 숫자 두 개, 태그 여러 개) 보니 공백기 채우기의 후보 UI를 그대로 가져다 쓰지 않고 새로 만들었다 — 억지로 하나의 틀에 맞추면 오히려 더 복잡해졌을 것이다.

## 통과하는 테스트, 멈추는 화면

백엔드 쪽은 새 질문 은행과 두 엔드포인트(다음 질문 묻기/현재 턴 확정하기)를 만들고 테스트를 돌렸는데, 6개 질문을 처음부터 끝까지 왕복하는 통합 테스트까지 포함해 전부 그린이었다. 그런데 실제로 브라우저를 띄워 e2e를 돌리자 4번째 질문(학력)에서 5번째(경력)로 못 넘어가고 멈췄다. 똑같은 흐름을 좁게 재현하는 디버그용 스펙을 따로 만들어 네트워크 요청을 전부 로깅하며 돌려봤더니 — 오히려 깨끗하게 통과했다. 서버 코드에는 문제가 없다는 뜻이었고, 아마 그날의 첫 번째 실행이 겪는 흔한 콜드스타트 지연이었을 가능성이 컸다.

같은 e2e를 다시 돌리자 이번엔 다른 곳에서 막혔다 — 6개 질문을 전부 답한 직후였다. 화면은 요약 화면 대신 곧바로 재편집 폼을 열어버렸고, 저장 버튼은 "저장 중..."에 멈춰 있었다. 이번엔 재현이 안정적이었다. 원인을 추적해보니, 마지막 질문에 답하고 나면 "질문 하나씩 묻는 컴포넌트"가 사라지고 그 자리에 "요약+재편집 컴포넌트"가 새로 나타나는데, 두 컴포넌트가 화면 아래쪽의 공용 채팅 입력창 상태(방금 보낸 메시지)를 공유하고 있었다. 새로 나타난 컴포넌트 입장에서는 "이미 처리된 메시지"와 "방금 도착한 새 메시지"를 구분할 방법이 없어서, 인터뷰 마지막 질문에 쓴 메시지를 자기한테 온 새 메시지로 착각하고 곧장 편집 폼을 열어버린 것이었다. 고침은 간단했다 — 새로 나타나는 컴포넌트가 태어나는 순간, 그때 이미 떠 있던 메시지는 "내가 볼 게 아니라 이미 처리된 것"으로 미리 표시해두면 됐다.

## 검증

백엔드 신규 테스트 10개를 포함해 185개 전부 통과, 프론트엔드 e2e도 고친 뒤 2회 연속 재현해 안정성을 확인했다. `eslint`/`next build`도 클린. 사용자가 확인하지 않은 값은 절대 저장하지 않는다는 원칙은 이번에도 그대로 — "특별히 없어요" 버튼으로 건너뛴 항목(예: 경력)은 요약 화면에 아예 표시되지 않는다.

## 남은 일

- 실제 워크넷 API 키로 진짜 검색 결과를 받아보는 확인은 여전히 남아 있다 — 지금까지는 mock 응답으로만 검증했다.
- 태그 편집기의 입력창 너비 계산이 한글 태그를 살짝 잘라 보여주는 자잘한 화면 버그를 발견했지만, 이번 작업 범위 밖이라 손대지 않았다.
