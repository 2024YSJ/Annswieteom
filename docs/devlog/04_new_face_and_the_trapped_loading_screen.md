# 20단계 — 새 얼굴을 입히고, "불러오는 중"에 갇힌 사람을 찾아내다

[03_the_agentic_interview_rebuild.md](03_the_agentic_interview_rebuild.md)에서 인터뷰 엔진을 다시 짜고 나니, 이번엔 화면 자체를 손볼 차례였다. 이 글은 세 갈래로 나뉜다 — 사소해 보이지만 실제로 자주 겪는 입력 방식 되돌리기, 두 번 갈아엎은 디자인, 그리고 마지막으로 "사이트가 멈췄다"는 신고를 받고 진짜 원인을 찾아낸 하루짜리 추적기다.

## 20-1단계 — 달력을 다시 꺼내다

공백기 기간을 입력하는 방식이 한동안 "언제부터 언제까지였나요?"라고 채팅창에 자유롭게 적으면 AI가 날짜로 해석해주는 방식이었다. 그런데 이건 애초에 있던 달력(날짜 선택기) 입력을 채팅 UI로 통일하는 과정에서 바뀐 것이었고, 사용을 해보니 그냥 달력에서 시작일·종료일을 고르는 쪽이 더 확실하고 빨랐다. 그래서 이 부분만 원래 방식으로 되돌렸다 — `PeriodSection` 컴포넌트가 더 이상 AI 해석을 거치지 않고 `<input type="date">` 두 개로 직접 값을 받는다. 공유 채팅 입력창도 이 단계에서는 아예 안 뜨게 했다(어차피 쓸 일이 없으므로).

같이 손댄 것: 브라우저 탭에 뜨는 이름이 계속 "Create Next App"(Next.js 기본값)이었다는 걸 발견해서 "안 쉬었음"으로 고쳤고, 검색엔진이 사이트를 더 잘 이해하도록 기본적인 메타데이터(설명, Open Graph, robots.txt, sitemap.xml)를 추가했다. 다만 "안 쉬었음"을 검색했을 때 상위에 뜨게 하는 건 코드만으로 되는 일이 아니다 — 실제 순위는 콘텐츠 양, 다른 사이트의 링크, 시간이 지나며 쌓이는 신뢰도 같은 요소가 훨씬 크게 작용하고, 특히 한국 사용자가 많이 쓰는 네이버는 네이버 서치어드바이저에 직접 사이트를 등록해야 색인이 시작된다. 이건 코드가 아니라 계정 소유자가 직접 해야 하는 일이라 이번 범위에서는 기반 작업만 해뒀다.

## 20-2단계 — 디자인을 두 번 갈아엎다

처음엔 "스케치 느낌 + 따뜻한 색감 + 정갈한 폰트"로 UI를 다듬어달라는 요청을 받고, roughjs라는 손그림 렌더링 라이브러리를 설치해 카드 테두리를 손으로 그린 듯하게 만들고, 크림색·황토색 계열 팔레트에 손글씨 느낌의 폰트를 입혔다. 그런데 다 만들고 보여드리니 "철회, 다 되돌려"라는 답이 왔다 — 대신 흰색·검정·빨강 기반의 사무적인 톤으로, 다만 UI가 너무 날카롭지 않게 해달라는 요청이었다.

여기서 배운 게 있다면, 커밋하지 않은 상태로 작업했던 게 신의 한 수였다는 점이다. `git checkout`으로 수정했던 파일들을 한 번에 원상복구하고 roughjs도 지운 뒤(`npm install`로 정리), 처음부터 다시 시작할 수 있었다. 실제 코드를 다시 만지기 전에, 먼저 시안(mockup)을 아티팩트로 만들어서 보여드렸다 — 색상 팔레트, 타이포그래피, 랜딩 화면과 세션 화면 목업까지. 이렇게 하면 실제 코드 전체를 다시 갈아엎기 전에 방향이 맞는지 확인할 수 있어서, 지난번처럼 "다 만들었는데 다시 하기"를 피할 수 있다.

승인받은 뒤 실제로 적용한 내용:
- 흰색 배경, 잉크에 가까운 검정 글자, 포인트로만 쓰는 빨강(주요 버튼·상태 배지·질문 라벨에만)
- 모서리는 8~9px 정도로만 둥글려서, 완전히 각지지도 않고 알약처럼 둥글지도 않게
- 제목/버튼은 Noto Sans KR 900굵기로 힘 있게, 본문은 400굵기로 편하게, 상태값·날짜처럼 "문서스러운" 자리에는 IBM Plex Mono를 섞어 사무적인 질감을 냄

폰트를 정하기 전에 상업적 이용이 가능한지도 확인했다 — Noto Sans KR과 IBM Plex Mono 둘 다 SIL Open Font License 1.1로, GitHub의 실제 라이선스 파일을 직접 받아서 확인했다. 상업적 이용·재배포·웹임베딩 전부 무료로 허용되고, 유일한 제약은 폰트 파일 자체를 단독 상품으로 되파는 것 금지뿐이라 웹폰트로 쓰는 이 서비스와는 무관하다.

## 20-3단계 — 입력창이 먼저 말을 걸게 하다

인터뷰 중 질문에 답할 때, 빈 입력창 앞에서 무슨 말을 써야 할지 막막한 느낌을 줄이고 싶다는 요청이 있었다. 그래서 AI가 질문을 던지는 동시에 "이렇게 답할 수도 있어요"라는 초안을 미리 입력창에 채워두는 기능을 만들었다. 백엔드에 `draft_answer`라는 새 LLM 호출을 추가해서, 지금까지 확인된 사실과 첨부된 기록물을 참고해 답변 초안을 한두 문장으로 만들고, 이걸 인터뷰 질문 응답(`interview/ask`)에 같이 실어 보낸다. 프론트에서는 공유 입력창이 이 초안을 그대로 편집 가능한 텍스트로 채워두고, 위에 "AI가 미리 써봤어요 · 이어 쓰거나 고쳐서 보내세요"라는 표시와 지우기 버튼을 붙였다.

여기서 중요한 건, 이 기능이 정직성 가드레일을 건드리지 않는다는 점이다. 입력창에 뭐가 미리 채워져 있든, 사용자가 보낸 답변에서 사실을 추출해 "확인/수정/제외"하는 절차는 그대로 거친다 — 즉 AI가 써준 문장을 그대로 보내도, 그게 곧바로 "확정된 사실"이 되는 게 아니라 기존과 똑같이 한 번 더 확인 단계를 거친다. 입력창을 미리 채우는 건 "빈 화면 공포"를 줄여줄 뿐, 확인 절차 자체를 건너뛰지 않는다.

## 20-4단계 — 모바일에서도 되나요

"모바일 버전도 가능해?"라는 질문에 확인해보니, 사이드바가 항상 오른쪽에 220px 고정폭으로 붙어있는 구조라 좁은 화면에서는 그냥 찌그러지고 있었다. 720px 이하에서는 사이드바를 화면 밖으로 밀어뒀다가(☰ 버튼을 누르면) 오른쪽에서 슬라이드로 열리는 드로어 방식으로 바꿨다. 이때 배운 점: Playwright로 전체 페이지(full page) 스크린샷을 찍었더니 상단 고정(position: fixed) 요소가 화면 중간에 유령처럼 한 번 더 나타나는 이상한 이미지가 나왔는데, 이건 실제 버그가 아니라 풀페이지 스크린샷 도구 자체의 고정요소 캡처 방식 때문에 생기는 촬영 아티팩트였다 — 뷰포트 크기를 충분히 크게 잡고 다시 찍어보니 깨끗했다. 화면을 눈으로 확인할 때도 "정말 화면에 그렇게 보이는지"와 "촬영 방식 때문에 그렇게 보이는지"를 구분해야 한다는 걸 새삼 확인한 순간이었다.

## 21단계 — "불러오는 중"에 갇힌 사람

배포하고 얼마 안 지나 "UI가 그대로인데?"라는 신고가 들어왔다. 처음엔 배포가 실제로 반영됐는지부터 의심했다 — GitHub의 배포 API로 최신 커밋이 Production으로 정상 배포된 걸 확인하고, 실제 서빙되는 HTML/CSS를 직접 받아서 새 폰트·색상 값이 들어있는 것까지 확인했다. 서버 쪽은 분명히 최신이었다. 그렇다면 남은 건 사용자의 브라우저 캐시였다.

그런데 대화가 이어지면서 증상이 구체화됐다 — "새로고침해도 계속 로딩 화면만 나온다"는 것이었다. 이건 단순 캐시로는 설명이 안 된다. 실제 프로덕션 사이트를 Playwright로 직접 열어서 로그인부터 세션 진입까지 재현해봤는데, 내 환경에서는 멀쩡했다. 그래서 코드를 다시 읽었고, 여기서 진짜 원인 두 가지를 발견했다.

**첫 번째: 에러 분기가 코드 순서 때문에 절대 실행되지 않고 있었다.**

```tsx
if (isLoading || !ctx) return <로딩 화면 />;   // 이게 항상 먼저 걸린다
if (loadError) return <에러 메시지 />;          // 그래서 이 줄은 죽은 코드였다
```

데이터를 불러오는 훅(react-query)은 요청이 "성공"하든 "실패"하든 `isLoading`을 `false`로 바꾼다. 문제는 실패했을 때도 `ctx`(데이터)는 여전히 `undefined`라는 점이다. 그러니 `isLoading || !ctx`라는 조건은 "아직 로딩 중"과 "완전히 실패함"을 구분하지 못하고 둘 다 참으로 처리해버린다. 결과적으로 뭔가 하나라도 실패하면 — 서버가 순간적으로 에러를 뱉든, 네트워크가 잠깐 끊기든 — 화면은 로딩 화면에서 절대 벗어나지 못했다. 첫 화면(홈)의 자동 리다이렉트 로직에도 똑같은 종류의 문제가 있었다: 세션 목록을 못 불러왔을 때를 아예 처리하지 않아서, 로그인된 사용자가 영원히 로딩 화면에 갇혔다.

**두 번째: 애초에 어떤 API 호출에도 타임아웃이 없었다.**

브라우저의 `fetch`는 기본적으로 타임아웃이 없다. 요청이 깔끔하게 실패하는 게 아니라 그냥 응답 없이 멈춰버리면(네트워크 어딘가가 조용히 연결을 끊거나 막는 경우), `fetch`가 반환하는 약속(Promise)은 영원히 완료되지 않는다. 위에서 고친 에러 처리도, 애초에 "에러"라는 상태 자체에 도달하지 못하면 아무 소용이 없다. 그래서 로그인 상태 확인, 세션 목록 조회, 세션 상세 조회 — 이 세 군데에 15초짜리 타임아웃을 걸어서, 무슨 일이 있어도 결국은 성공이든 실패든 결론이 나도록 만들었다.

이 두 가지를 실제로 강제 재현해서 확인했다 — 응답을 일부러 실패시키거나 응답 자체를 지연시켜보니, 고치기 전에는 화면이 "불러오는 중"에 그대로 멈췄고, 고친 뒤에는 몇 초 안에 에러 메시지와(홈 화면의 경우) "다시 시도" 버튼이 정상적으로 떴다.
