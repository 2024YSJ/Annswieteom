# 31~33단계 — 게스트 세션이 두 번 생기던 진짜 이유, 질문 예산 되돌리기, 문단화

## 31단계 — "새로고침하면 세션이 두 개가 된다"

이번엔 재현이 쉬웠다 — `app/page.tsx`를 다시 읽어보니, 게스트 시작 버튼(`handleGuestStart`)이 `guestLogin()` 다음에 자기 손으로 `sessionApi.create()`를 부르고 있었는데, 바로 그 `guestLogin()`이 `user` 상태를 바꾸는 순간 페이지의 자동 리다이렉트 `useEffect`(세션이 비어있으면 첫 세션을 만드는 로직)도 **똑같은 트리거로 독립적으로 발동**하고 있었다. 둘 다 "이 사람은 세션이 없으니 하나 만들자"를 각자 판단해서, 타이밍에 따라 종종 두 개를 만들었다. 고친 방식은 버튼 핸들러에서 세션 생성/이동 코드를 아예 들어내고, "세션이 없으면 만들고 이동한다"는 책임을 그 effect 하나에만 남긴 것이다. Playwright로 게스트 시작을 6번 연속 재현해서 매번 세션이 정확히 1개만 생기는 걸 확인했다.

## 32단계 — 3회는 너무 빡빡했다

바로 직전 단계에서 카테고리당 총 질문 수를 3으로 낮췄었는데, 곧바로 "프로젝트 → 그 목적 → 그게 왜 중요했는지"처럼 여러 단계로 파고드는 질문이 더 자주 나오게 해달라는 요청이 왔다. 3개 예산으로는 고정 질문 하나 쓰고 나면 파고들 여지가 1~2번뿐이라 애초에 여러 단계 체인이 거의 불가능했다. 6으로 다시 올리고, 파고들기 프롬프트(`interview_drilldown.jinja`)도 "막연한 답만 캐묻기"에서 "표면적 사실 → 목적 → 더 근본적인 이유"로 계속 이어서 파고드는 걸 적극적으로 추구하도록 다시 썼다 — 사용자 스스로도 언어화하지 못했을 잠재력/동기를 끌어내는 게 목표라는 걸 프롬프트에 명시했다.

## 33단계 — "내보내기 품질이 떨어진다"

문서 생성 코드를 보니 원인이 바로 보였다 — 카테고리 하나당 LLM을 한 번 불러서 `sentences: [...]`라는 완전히 평평한 문장 목록을 받고, 그걸 그대로 줄바꿈만 해서 이어붙이고 있었다. 문단도, 소제목도, 관련성 표시도 없었다.

해결책은 세 갈래로 나눴다: ① `GeneratedParagraph`라는 새 테이블을 만들어 문장들을 주제별로 묶고, ② LLM 프롬프트를 "같은 카테고리 안에서 다른 에피소드끼리는 별도 문단으로, 같은 흐름이면 한 문단으로" 나누도록 다시 쓰고, ③ 확정 전에 사용자가 그 그룹핑을 확인/조정할 수 있는 조작 3가지(문단 제목 수정 + 확인 표시, 인접 문단 합치기, 문장을 옆 문단으로 옮기기)를 추가했다. 내보내기는 문단 사이에 빈 줄을 넣어 구분하되, 문단 제목 자체는 이력서 문체에 안 맞아서 리뷰 화면에서만 보여주고 내보낸 텍스트에는 안 넣었다.

구현 중 실제 버그를 하나 잡았다 — 인접 문단을 합칠 때 문장들의 `paragraph_id`를 새 문단으로 옮기고 나서 옛 문단을 삭제했는데, DB의 `ON DELETE CASCADE`가 SQLAlchemy의 UPDATE가 실제로 반영되기 전에 발동해서 옮기려던 문장들이 통째로 같이 삭제돼버렸다. `delete()` 전에 명시적으로 `flush()`를 넣어서 UPDATE가 먼저 DB에 반영되도록 고쳤다 — 테스트로 바로 잡아낸 케이스.

이 김에 `generate_document()`의 오래된 버그도 같이 고쳤다 — 카테고리 라벨 자리에 `facts[0].fact_type`을 잘못 쓰고 있던 것을 실제 카테고리 라벨을 넘기도록 바꿨다(이전 계획 문서에 "선택 사항"으로 남겨뒀던 부수 발견).

로컬 개발 DB 마이그레이션을 적용하려는 중에 또 한 번 `.env`의 DB 비밀번호가 안 맞는 상황을 만났다 — dev Supabase 프로젝트 비밀번호가 그 사이 바뀐 것으로 보인다. 사용자가 새 값을 넣어준 뒤, 프리픽스(`postgresql://` → `postgresql+asyncpg://`)만 다시 보정해서 해결했다.

## 34단계 — 이번엔 마이그레이션을 잊지 않았다

지난번(`06_...md`) 사고의 교훈대로, `main`에 머지하자마자 바로 "프로덕션 DB에 `c4e8a2f1d6b3` 마이그레이션을 적용해야 한다"고 먼저 알렸다. `alembic upgrade head`를 실행할 프로덕션 연결 문자열을 받는 대신, 사용자가 Supabase SQL Editor에 직접 실행할 수 있도록 마이그레이션과 동등한 SQL(`CREATE TABLE generated_paragraphs ...`, `ALTER TABLE generated_sentences ADD COLUMN paragraph_id ...`)을 그대로 제공했다.

실행 과정에서 Supabase Studio가 "새 테이블에 Row Level Security가 꺼져 있다"는 경고를 띄웠다. 기존 마이그레이션들을 확인해보니 `users`/`sessions`/`confirmed_facts` 등 어떤 테이블에도 RLS가 켜져 있지 않았다 — 이 앱은 프론트가 Supabase에 직접 접속하지 않고 항상 FastAPI 백엔드를 거쳐서만 데이터에 접근하므로(권한 검사도 전부 백엔드 코드에서 처리), RLS는 이 아키텍처에서 실제로 아무것도 막아주지 않는다. 정책 없이 켰다가 오히려 백엔드 접근 방식에 따라 예상 못 한 차단이 생길 수 있어서, 기존 테이블들과 일관되게 RLS 없이 그대로 진행하도록 안내했다.

SQL 실행 후 실제 프로덕션에 다시 요청을 보내 카테고리 선택이 정상 작동하는지(마이그레이션 누락 시 500이 났던 지점) 확인했다 — 정상.
