# Phase 2 — 통합 채팅 UI

Claude-Desktop형 UI 재설계 로드맵의 두 번째 단계. [Phase 1](phase1_guest_sessions_and_sidebar.md)에서 게스트 세션과 사이드바를 붙였다면, 이번엔 기간입력·카테고리선택·기록물업로드·인터뷰·결과 5개 페이지를 하나의 연속된 채팅형 화면으로 합친다. **백엔드 상태머신/API는 전혀 바꾸지 않는다** — 순수 프론트엔드 재배치다.

## 목표

1. `/sessions/{id}/period`, `/categories`, `/records`, `/interview`, `/result` 5개 라우트를 `/sessions/{id}` 하나로 통합
2. 각 단계는 완료되면 요약 말풍선으로, 진행 중이면 실제 폼으로 한 화면 안에 순서대로 표시
3. 최종 생성 문서(톤슬라이더·근거태그 포함)를 별도 페이지가 아니라 같은 화면의 인라인 메시지로 표시

## 핵심 설계: "완료/진행 중" 두 모드를 갖는 섹션

백엔드가 순수한 순방향 상태머신(상태가 되돌아가지 않음)이라는 점에 기대어, 5개 단계를 각각 `PeriodSection`/`CategorySection`/`RecordsSection`/`InterviewSection`/`ResultSection` 컴포넌트로 만들고 각각 두 모드만 갖게 했다:

- **completed**: 사용자가 이미 제출한 내용을 오른쪽 정렬 요약 말풍선으로 보여줌
- **active**: 실제 폼(오늘의 페이지와 동일한 상태/검증/API 호출)을 넓은 카드로 보여줌

아직 도달하지 않은 단계는 **아예 렌더링하지 않는다**(숨겨서 마운트만 해두지 않음) — 그렇게 하지 않으면 폼이 안 보이는 채로 계속 마운트돼 있다가 상태가 바뀔 때 그 안의 effect(예: `interview/next` 중복 방지 로직)가 예상치 못한 타이밍에 도는 위험이 있다.

범용 "채팅 메시지" 유니온 타입 아키텍처는 의도적으로 채택하지 않았다 — 지금 백엔드는 메시지 스트림이 아니라 상태머신이라 그런 설계는 과설계다. Phase 3에서 진짜 자유 대화가 들어오면 그 부분에 한해 별도로 도입하고, 지금의 섹션 모델과 공존시키면 된다.

## 라우팅

- `frontend/app/sessions/[id]/page.tsx` 하나로 통합, 예전 5개 서브라우트 폴더는 삭제
- 예전 URL로의 리다이렉트는 만들지 않음 — 아직 실사용자가 없는 프로토타입 단계라 의도적으로 생략
- `pathForStatus`는 삭제(더 이상 여러 라우트가 없으므로). 대신 `session-routes.ts`에 `INTERVIEW_STATUSES`/`RESULT_STATUSES` 상수를 공용으로 뺐다(예전엔 `interview/page.tsx`·`result/page.tsx`에 각각 로컬로 있었음)

## 오케스트레이터의 책임

`sessions/[id]/page.tsx`가 `useSessionContext`를 **한 번만** 호출하고 그 `ctx`를 5개 섹션에 prop으로 내려준다(예전처럼 각 페이지가 따로 조회하지 않음). 5개 불리언(`periodDone`/`categoriesDone`/`recordsDone`/`interviewActive`/`resultActive`)으로 어느 섹션까지 렌더링할지 결정하고, 다음을 직접 담당한다:

- 사이드바 진행 상태 갱신: 예전엔 라우트가 바뀔 때(`usePathname`) 사이드바 쿼리를 무효화했는데, 이제 한 세션 안에서는 URL이 안 바뀌므로 `ctx.status` 변화를 감지하는 별도 effect를 추가했다. `sessions/layout.tsx`의 기존 `pathname` 기반 무효화는 그대로 남겨뒀다(다른 세션으로 이동할 때는 여전히 필요).
- 새 섹션이 나타날 때 자동 스크롤 + `aria-live="polite"`로 스크린리더에 알림 + 포커스 이동 — 페이지 전환이 없어지면서 사라진 "새 화면 진입" 신호를 보완

## 인터뷰 스레드의 다중 카테고리 확장

기존 `InterviewChatThread`는 `confirmedFacts: ConfirmedFactRead[]` 하나만 받아서 **그 시점의 카테고리 하나 분량**만 보여줬다(페이지 자체가 카테고리마다 다시 로드됐으므로 그걸로 충분했음). 이제 여러 카테고리가 한 화면에 이어져야 하므로 prop을 `categories: ActivityCategoryRead[]` + `currentCategoryId`로 바꿔서, 이미 확인된 사실이 있거나 지금 진행 중인 카테고리만(아직 도달 안 한 카테고리는 안 보이게) 구분선과 함께 순서대로 보여주도록 일반화했다.

## 자잘한 개선

- `RecordsSection`의 진행 버튼 문구: 이번 방문에서 기록물을 하나라도 등록했으면 "다음으로", 없으면 기존 "기록물 없이 넘어가기" — 호출하는 엔드포인트(`records/skip`)는 동일하지만, 실제로 기록물을 올리고 나서도 "없이 넘어가기"라고 뜨는 게 어색했던 부분을 고쳤다. `RecordUploadPanel`에 `onRecordsChange?` prop을 추가해서 이 개수를 부모가 알 수 있게 했다.
- `RecordsSection`의 completed 요약은 개수를 표기하지 않는다 — 세션의 기록물 목록을 다시 조회하는 엔드포인트가 없어서, 새로고침 이후엔 정확한 개수를 재구성할 방법이 없다. 틀린 숫자를 보여주느니 "기록물 업로드를 완료했어요"라는 일반적인 문구를 쓴다.
- 페이지 전환이 사라지며 예전엔 각 페이지의 실제 제목이던 `<h1>`들이 한 페이지에 5개 이상 몰리게 된다 — heading 랜드마크가 아니라 강조 텍스트로 격하했다.

## 의도적으로 처리하지 않은 것 (Phase 2 범위 밖)

- 예전 5개 URL에 대한 리다이렉트
- 오래된 "completed" 말풍선들을 접어서 화면을 짧게 유지하는 기능(세션이 길어지면 스크롤이 매우 길어질 수 있음 — 나중 폴리시 이슈로 남김)
- 기록물 업로드를 채팅 입력창으로 옮기는 것(Phase 4 몫)
- AI가 자유 대화에서 카테고리를 추출하는 것(Phase 3 몫) — 지금은 여전히 체크박스로 직접 선택
