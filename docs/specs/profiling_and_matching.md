# 대화 기반 프로파일링 + 교집합/합집합 맞춤 매칭

2026-09-11 요청: 사용자를 거의 프로파일링하다시피 정보를 모아, 그 정보로 맞춤 취업 정보·청년 혜택을 찾아준다.

1. 대화를 유동적이고 정교하게 만들어 사용자가 자연스럽게 정보를 말하게 한다. 얻은 정보는 이후 대화에 쓰이고 사용자 정보로 저장돼야 한다.
2. 추천은 사용자 정보의 **교집합**(모든 조건 충족) 공고를 우선하되 **합집합**(일부 충족) 공고도 찾는다.

## 출발점 — 무엇이 없었나

- 인터뷰는 **활동 사실**(`confirmed_facts`)만 저장했다. 나이·거주지·학력·전공·취업상태·희망직무 같은 **사람 단위 속성은 어디에도 없었다.** 사용자 쪽 정보는 자유 텍스트 `wish_text` 하나뿐이었다.
- 맞춤 공고는 프로필 텍스트 한 덩어리를 bge-m3 벡터 하나로 만들어 코사인 정렬만 했다. "경기 남부 + 반도체 + 신입"이 평균된 한 방향이 되어 **교집합이라는 개념 자체를 표현할 수 없었다.**
- 온통청년 API는 자격조건 필드(연령·지역·학력·전공·취업상태·특화분야·혼인·소득)를 **이미 주고 있었는데** 파서가 버리고 있었다.

## 설계 원칙

1. **정직성 가드레일은 그대로다.** 속성은 추천과 대화 보조에만 쓴다. 생성 문서는 여전히 `confirmed_facts`만 인용한다. 대화 주입은 `followup_question`·`judge_drilldown`에만 한다 — `draft_answer`에 넣으면 추정 속성이 AI 초안에 섞이고, 사용자가 무심코 확인하는 순간 confirmed_fact로 세탁된다.
2. **LLM은 코드를 외우지 않는다.** 프롬프트에는 라벨 목록만 주고 코드는 서버가 붙인다(`regions.py`와 같은 원칙).
3. **근거 인용 필수.** 속성마다 사용자 원문 인용을 요구하고, 원문과 충분히 겹치지 않으면 버린다. 지역과 자유 텍스트 값은 값 자체가 원문에 있어야 한다.
4. **민감정보는 서버가 막는다.** 동의가 없으면 값을 저장하지 않고 "말했다"는 표시만 남긴다. 동의를 철회하면 즉시 완전 삭제한다.
5. **"제한없음"이 교집합을 잠식하지 않게.** 필드 판정을 `match / open / unknown / mismatch` 넷으로 나누고, 교집합은 명시 일치가 1개 이상이어야 한다.
6. **요청 경로의 LLM 호출은 늘리지 않는다.** 추출은 응답 뒤 BackgroundTasks에서 돈다.

## 데이터 모델

`user_attributes` — 속성 한 값 = 한 행.

| 컬럼 | 뜻 |
|---|---|
| `key` | 비민감: `birth_year, residence_region, desired_region, education_level, major_field, employment_status, desired_job, desired_employment_type, skills*, certificates*, interests*` / 민감: `annual_income, special_groups*, marital_status` (*다중값) |
| `value` | `{"label": "수원", "code": "41110"}` 식. 코드는 온통청년 체계 |
| `status` | `inferred`(대화 추정) / `confirmed`("맞아요") / `user_edited`(직접 수정·입력) / `rejected`(삭제 — 같은 값을 다시 추정하지 않기 위해 남긴다) |
| `evidence_text` | 추정 근거가 된 사용자 본인의 말. 원 답변을 지우면 같이 지운다 |
| `invalidated_at` | 새 추정이 옛 추정을 대체하면 찍힌다(이력 보존). 활성 = NULL |

`user_consents` — `sensitive_profiling` 동의. `sensitive_mentioned_at`은 동의 없이 민감정보를 말했을 때 찍힌다.

`feed_items.eligibility` — 온통청년 자격조건 코드(JSON). 매칭 입력.

## 흐름

```
사용자 발화 ─┬─ 인터뷰 답변 (interview_answer)
            ├─ 구직 검색 질문 (query_job_info)
            └─ 희망사항 저장 (put_preferences)
                 │  BackgroundTasks — 응답 뒤
                 ▼
     extract_profile_attributes (LLM, temperature 0)
                 ▼
     validate_candidates — 인용 대조 / 지역·자유텍스트 원문 대조 / 민감정보 차단
                 ▼
     reconcile (규칙) — NOOP · 사용자 값 보호 · 추정끼리 교체 · 삭제값 부활 금지
                 ▼
            user_attributes ──┬─→ /archive 편집 화면 (확인·수정·삭제·동의)
                              ├─→ 인터뷰 후속/드릴다운 프롬프트 (비민감만)
                              └─→ /feed/policies/recommended 티어 매칭
```

## 매칭 (`services/feed/matching.py`)

| 필드 | 하드/소프트 | 판정 |
|---|---|---|
| 나이 | 하드 | 0·1은 하한 없음, 0·99+는 상한 없음. 출생연도만 알아 만 나이가 ±1이고, API 연령이 원문과 한 살씩 어긋나는 경우가 있어(화순군 원문 18~49 → API 17~48) **경계 ±1년은 unknown** |
| 거주지 | 하드 | 250개 이상 코드 = 전국(open). 시 코드(41110)는 구 코드(41111…)와 **앞 4자리**로 비교. 광역만 아는 사용자는 광역 전체를 덮으면 match, 일부면 unknown |
| 혼인 | 하드(민감) | 0055003 = 제한없음 |
| 학력·전공·취업상태 | 소프트 | 목록에 있으면 match, 없으면 mismatch, 사용자 값 모르면 unknown |
| 특화분야 | 소프트(민감) | 사용자가 해당한다고 말하지 않은 건 **unknown**(불일치 증거가 아니다) |
| 소득 | 소프트(민감) | 0043002만 금액 비교, 0043003(자유 텍스트)은 unknown |

티어: `all`(교집합: 불일치·미확인 없음 + 명시 일치 ≥1) → `some`(합집합: 명시 일치 ≥1) → `none`(명시 일치 0, 벡터 유사도순) → `excluded`(하드 불일치, 기본 숨김). 정렬 키 `(티어, -명시일치수, 불일치수, 벡터거리, -최신, id)` — 완전 결정적이라 limit/offset 페이지가 겹치거나 빠지지 않는다.

## 온통청년 코드표 (2026-09-11 검증)

코드표 원본(API코드정보.xlsx)은 로그인 뒤에만 받을 수 있어 `backend/scripts/tally_youthcenter_codes.py`로 2,673건의 분포와 코드별 샘플 정책을 뽑아 통합검색 화면의 선택지 순서와 대조했다.

- 모든 필드에서 **가장 흔한 코드 = 마지막 번호 = "제한없음"**(학력 0049010 2,304건 등). 화면은 "제한없음"을 맨 앞에 두지만 코드는 맨 뒤다.
- 나머지는 화면 순서대로 001부터. 의미가 명확한 샘플로 확인: 특화 004 한부모("청년한부모 자녀양육비"), 007 군인("군복무 상해보험"), 혼인 001 기혼("신혼부부 주거자금"), 전공 005 공학("반도체 특성화 대학").
- `sprtTrgtAgeLmtYn`은 믿을 수 없다 — Y·N 모두 실제 연령 범위와 함께 왔다. min/max가 0인지로만 판단한다.
- **광주·전남은 2026년 통합으로 zipCd 12(전남광주통합특별시)** 를 쓴다. 29/46은 0건이었다. 사용자 쪽 29/46은 매칭 시 12로 바꾼다(`REGION_ALIASES`). `regions.py`는 고용24용이라 그대로 둔다.
- 전국 정책은 256개 시군구 코드를 통째로 나열한다.
- 온통청년은 매번 다른 페이지 하나에서 400/403을 낸다 — 수집은 실패 페이지 이후를 버리고 이미 받은 것은 남긴다.

## 개인정보

- 장애는 개인정보보호법상 민감정보(건강, 제23조). 소득·수급·한부모·혼인도 같은 무게로 동의 게이트.
- 비민감 속성도 편집 화면에 수집·이용 목적을 고지한다(제15조).
- 동의는 가입 계정만(게스트는 기기에 묶여 삭제 수단을 잃을 수 있다). 철회 = 즉시 완전 삭제.
- 민감 속성은 `user_profile_embeddings.profile_text`(평문 디버그 컬럼)에 넣지 않는다.

## 2단계 로드맵 (시연 후)

1. **동적 슬롯 플래너** — 사용자별 슬롯 커버리지, 카테고리 전환 시점에 빈 슬롯 질문 최대 1개, ~80% 채우면 중단. 가설추론형 질문.
2. **능동적 경청** — 질문 앞에 직전 답변 한 줄 반영(OARS).
3. **동의 후 민감 질문**을 인터뷰 안에서.
4. **세션 간 기억** — 다른 세션 문답 요약까지 `_build_context`에.
5. **상태 있는 구직 채팅** — 저장된 희망 지역·직무로 검색 조건 프리필.
6. **고용24 wk/* 카테고리 필터와 공고 자격 파싱** — 지금 티어 매칭은 온통청년 정책만.
7. LLM 기반 충돌 조정, 속성 이력 뷰, 추출 F1 오프라인 평가셋.
