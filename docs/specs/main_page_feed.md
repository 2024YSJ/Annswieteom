# 메인 화면 피드 (청년 지원 정책 / 공고 / 맞춤 공고)

원래 마일스톤 체크리스트에 없던 항목. 대응 devlog: [PersonB/25_main_page_feed.md](../devlog/PersonB/25_main_page_feed.md).
같이 진행한 Gemini 제거는 [PersonB/24_remove_gemini_no_fallback.md](../devlog/PersonB/24_remove_gemini_no_fallback.md).

## 목표

취업 정보가 지금은 `job_search` 세션 안에서 **사용자가 먼저 질문해야만** 나온다. 뭘 물어야 할지 모르는 사용자에게는 아무것도 안 보인다. 질문 없이 먼저 보여주는 읽기 전용 피드를 만든다.

1. **청년 지원 정책** — 최신 등록순
2. **공고** — 최신순, 로그인 여부 무관
3. **맞춤 공고** — 계정에 쌓인 문답으로 개인화

## 데이터 모델

| 테이블 | 역할 |
|---|---|
| `feed_items` | 외부 API에서 긁어온 항목 캐시. **전 사용자 공용** — 같은 공고는 누구에게나 같은 항목이고 다른 건 정렬 순서뿐이다. 벡터 컬럼 없음 |
| `feed_item_embeddings` | 항목 벡터(PK=FK, 1:1) |
| `user_profile_embeddings` | 사용자 프로필 벡터(PK=FK, 1:1). **우리 소유의 파생 캐시** |
| `feed_refresh_states` | 소스별 갱신 상태 + 시간 기반 동시 갱신 락 |

`feed_kind`(`job`/`policy`)는 파생값이 아니라 실제 컬럼이다. 메인 화면이 두 섹션으로 갈리고, 각 섹션이 자기 풀 안에서만 독립적으로 정렬돼야 하기 때문이다. 이 축이 "코사인 정렬하면 한 카테고리가 화면을 다 먹는" 문제도 같이 해결한다 — 별도 다양성 로직 없이.

### 벡터를 곁테이블로 뺀 이유

pgvector의 `Vector`는 SQLite 컴파일러가 없다. `feed_items`에 벡터를 얹으면 `tests/api/conftest.py`가 그 테이블을 만들 수 없고 **피드 API 전체가 API 레이어에서 테스트 불가능**해진다(`record_chunks`가 대부분의 픽스처에서 빠져 있는 것과 같은 이유).

대가는 둘이다. (1) 개인화 조회에 조인 하나. (2) **실제 코사인 정렬은 자동 테스트로 못 덮는다** — SQLite에서 검증할 방법이 없고 Postgres 테스트 컨테이너는 이번 범위 밖이다. 수동 검증(아래)으로만 확인한다.

### 중복 제거

`dedup_key`는 소스가 안정적인 id(또는 항목 고유 상세 URL)를 주면 `k:<id>`, 없으면 제목+부제+메타의 sha256 `h:<hash>`.

id 없는 카테고리(채용행사/공채기업정보/구직자프로그램/강소기업)는 소스가 문구를 한 줄만 고쳐도 새 항목으로 들어온다. 반대로 키를 느슨하게 잡으면 진짜 새 공고를 조용히 삼킨다. **중복 카드는 보이는 실패, 누락은 안 보이는 실패**라 보이는 쪽을 택했다. 그래서 옛 행은 삭제가 아니라 `is_active=False`로 내려가고 14일 뒤에 정리된다.

워크넷 응답에는 채용행사의 `eventNo`, 공채속보의 `empSeqno`가 실제로 들어 있다. 지금 `JobInfoResult`가 그 필드를 안 들고 있어서 못 쓰고 있고, 그 파일을 동시에 크게 고치는 작업이 있어 병합 후로 미뤘다. **후속 작업 1순위.**

## 수집·갱신 (stale-while-revalidate)

- TTL 6시간(`FEED_REFRESH_TTL_SECONDS`). 만료된 소스가 있으면 조회 요청이 `BackgroundTasks`로 갱신을 예약하고 **응답은 캐시에서 즉시 나간다.**
- 동시 갱신 락은 `feed_refresh_states.last_started_at` 조건부 UPDATE(CAS). 없으면 동시 접속 수만큼 갱신이 떠서 심사받아 얻은 API 쿼터를 그만큼 태운다. 불리언이 아니라 시각이라 워커가 죽어도 10분 뒤 저절로 풀린다.
- **소스 하나의 실패가 나머지를 막지 않는다.** 실패는 그 `source_key`에만 기록된다.
- **임베딩은 fetch 성공 여부와 무관하게 항상 돌고, 실패해도 갱신을 실패로 만들지 않는다.** 항목은 임베딩 전에 커밋되므로 터널이 끊겨도 피드는 최신순으로 살아 있고, 같은 루프가 다음 갱신 때 빈 벡터를 backfill한다.
- ⚠️ **콜드 스타트 최초 1회는 구조적으로 빈 응답이다.** `BackgroundTasks`는 응답을 보낸 뒤에 실행된다. `is_warming: true`로 알리고 프론트가 재조회한다. 버그가 아니다.

## 랭킹

- 개인화 입력은 `interview_answers`(계정 단위 문답 아카이브)의 **자유 텍스트**다. 옛 `job_search_preferences` 같은 구조화 필드는 존재하지 않고, 그게 오히려 낫다 — "경기 북부"를 "의정부/파주"에 매핑하는 표를 손으로 만들 필요 없이 bge-m3가 의미로 붙인다(devlog 18의 교훈).
- `question_text`는 **일부러 뺀다.** 시스템이 만든 문구라 사용자 간에 거의 같아서, 넣으면 모든 프로필 벡터에 공통 성분이 생겨 개인화가 뭉개진다.
- 미확정 답변도 **포함한다.** 정직성 가드레일은 "생성 문서가 무엇을 인용할 수 있는가"를 규율하고(`document_generator`는 여전히 `confirmed_facts`만 받는다), 어떤 공개 공고를 위로 올릴지는 그 대상이 아니다. 피드는 문장을 만들지도 인용하지도 않는다.
- 읽기 경로는 **절대 임베딩 호출을 기다리지 않는다.** 벡터가 없으면 최신순으로 응답하고 계산만 백그라운드로 예약한다.

### 개인화가 안 될 때 — 세 상태를 구분한다

| 상황 | `fallback_reason` | 화면 |
|---|---|---|
| 정상 | `null` | 맞춤 공고 |
| 문답 0건 | `no_profile` | "공백기 정리를 해보시면 맞춤 공고를 찾아드려요" |
| 문답은 있고 벡터 아직 없음 | `preparing` | "맞춤 정보를 준비하고 있어요" |
| 벡터는 있는데 정렬 질의 실패 | `ai_unavailable` | "AI 서버가 수리 중이예요." |

`preparing`을 따로 둔 건 라이브 검증에서 잡은 문제 때문이다. **문답을 처음 남긴 사용자는 전부 이 경로를 한 번 지나가는데**, 처음엔 여기에 고장 안내가 떴다 — 정상 동작에 오경보였다.

어느 경우든 `items`는 최신순으로 채워지므로 **화면이 비지 않는다.**

## API

| 엔드포인트 | 인증 | 정렬 |
|---|---|---|
| `GET /api/v1/feed/policies` | 익명 허용 | `coalesce(source_published_at, first_seen_at)` desc |
| `GET /api/v1/feed/jobs` | 익명 허용 | `first_seen_at` desc |
| `GET /api/v1/feed/jobs/recommended` | 인증 필요(게스트 포함) | 코사인, 불가 시 최신순 |
| `GET /api/v1/feed/sources` | 인증 필요 | 정렬 없음 — 소스별 설정/수집 상태(진단용) |

- 파라미터: `limit`(1~50, 기본 20), `offset`(≥0), `category`. `api/profile.py`가 세운 선례를 따른다.
- 정렬에는 항상 `FeedItem.id` 타이브레이커를 붙인다 — 한 수집 배치는 `first_seen_at`이 마이크로초까지 같아서, 없으면 페이지가 조용히 겹치고 새어나간다.
- `/me`가 아니라 `/feed`인 이유: `/me`는 문답 아카이브 라우터가 점유했고, 무엇보다 **피드는 로그아웃 방문자에게 떠야 하는데 `/me/*`는 정의상 인증이 필요하다.**
- **게스트를 403하지 않는다.** `api/profile.py`는 막지만 그건 "세션을 넘어 쌓인 아카이브"가 게스트에겐 성립하지 않아서다. 랭킹은 신호가 조금이라도 있으면 이득이고, 돌려주는 건 공개 공고뿐이라 사용자 텍스트가 밖으로 나가지 않는다.

### 실패 모드

| 상황 | 응답 |
|---|---|
| 소스 일부 실패 | 200, 항목이 그만큼 적다 |
| 소스 전부 실패 + 캐시 있음 | 200, 캐시 그대로 |
| 소스 전부 실패 + 캐시 없음 | 200, 빈 목록 + `is_warming: true` |
| 임베딩 서버 다운 | 200, 최신순 + `preparing`/`ai_unavailable` |

**피드는 소스 실패로 503을 내지 않는다.** 캐시를 두는 이유가 그것이다. 새 에러 코드는 `invalid_feed_category`(422) 하나뿐이다.

## 범위 밖 / 후속

- `JobInfoResult.source_key`(`eventNo`/`empSeqno`) — 병합 후 1순위.
- ~~`GET /feed/sources`~~ — 2026-09-09 추가했다. 처음엔 "자를 순서 1번"으로 잘랐는데, 실제로 피드가 비었을 때 원인을 못 찾아 프로덕션 API를 손으로 쳐야 했다.
- ivfflat 인덱스 — 수백 행 규모에서는 seq scan이 더 빠르다. 데이터가 쌓이면 init 마이그레이션과 같은 raw SQL 형태로 추가.
- 프론트 연동 전체(`lib/api/feed.ts`, 메인 화면 섹션). ⚠️ `app/page.tsx`가 **세션이 1개 이상인 로그인 사용자를 곧바로 최근 세션으로 리다이렉트**한다 — 즉 프로필이 쌓인 바로 그 사용자가 랜딩을 못 본다. 피드를 어디에 놓을지부터 정해야 한다.
- `GET /feed/*`는 이 앱 최초의 무인증 데이터 엔드포인트다. `limit ≤ 50` 인덱스 조회에 공개 데이터뿐이라 괜찮다고 판단했지만, 실수가 아니라 결정이었음을 남겨둔다.
